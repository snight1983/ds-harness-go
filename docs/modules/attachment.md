# 附件与图片

对应包：`attachment`、`adapter/imagestore`

## 定位

人跟 agent 说话的时候会贴一张截图：「这个报错是什么意思」。这一下看着简单，麻烦全在后面——那张图有好几兆，而会话日志要被反复读、反复回放、还要送到客户端去。

```mermaid
flowchart LR
    subgraph N["把图片字节直接塞进会话日志"]
        A1["人贴一张 3 兆的截图"] --> A2["日志里多出 4 兆的 base64"]
        A2 --> A3["同一张图在十轮对话里<br/>被重复存了十次"]
        A2 --> A4["每次列一下历史<br/>都要把这几兆搬一遍"]
    end
```

```mermaid
flowchart LR
    subgraph Y["日志里只放一张收据"]
        B1["人贴一张 3 兆的截图"] --> B2["字节存到别处"]
        B2 --> B3["日志里只留一行收据<br/>标识、格式、多大、多少像素"]
        B3 --> B4["要看图的时候<br/>凭收据回去取"]
    end
```

这两个包管的就是**那张收据**：怎么发、发出去之前要验什么、凭它怎么把字节取回来、以及取回来的东西凭什么相信还是当初那一张。

### 为什么这里不能说「路径」

一般人第一反应是「图存成一个文件，日志里记文件名」。这条路在本仓库走不通：

```mermaid
flowchart TD
    A["服务端"] --> B["没有硬盘"]
    B --> C["也就没有目录、没有文件名<br/>没有「上一级」这个概念"]
    C --> D["字节的去处只有两种：<br/>数据库，或者对象存储"]
    E["「存到 DSH_HOME 底下」"] -.->|"那是桌面工具的答案<br/>这台服务多副本部署，没有一个共同的本机磁盘"| D
```

所以收据上写的不是路径，是一个**不透明标识**——它长什么样、怎么换回字节，只有存储那一侧知道。

## 架构

```mermaid
flowchart TD
    UP["浏览器上传<br/>base64 载荷"] --> ADM["准入口<br/>剥掉 base64 那层壳"]
    ADM --> BATCH["整批规矩<br/>几张、加起来多大、什么格式"]
    BATCH --> ONE["逐张校验<br/>真解一遍，看它是不是图"]
    ONE --> SAVE["逐张提交"]
    SAVE --> REF["收据"]
    REF --> LOG[("会话日志")]
    REF --> READ["按收据取回字节"]
    REF --> PROJ["派生请求版本<br/>可选能力"]
    SAVE -.->|"字节真正落在哪儿"| MEDIA[("对象存储 / 数据库")]
```

两个包的分工：

| 包 | 它管的 | 它明确不管的 |
|---|---|---|
| `attachment` | 词汇、**次序规矩**、失败分类 | 一个字节都不存 |
| `adapter/imagestore` | 字节怎么落、怎么取、怎么核对 | 不决定模型收不收图 |

### 两层图，不能混成一层

```mermaid
flowchart TD
    SRC(("人传上来的那张图")) --> L1["第一层：存下来的那一张<br/>跟任何模型提供方无关"]
    L1 --> L2A["第二层：给 A 家模型的版本<br/>按它的像素和字节预算重编一份"]
    L1 --> L2B["第二层：给 B 家模型的版本<br/>预算不一样，重编的结果也不一样"]
    L1 --> LOG[("只有第一层进会话日志")]
```

**为什么非要分开**：同一张图会被送给好几家模型，各家的预算不一样。如果日志里存的是「给 A 家裁好的那一份」，那么换一家模型、或者 A 家明天改了限额，整段历史就全废了。第二层是**派生出来的**，随时可以重新算；第一层是事实，只算一次。

第二层带一个确定性标识：同一张图配同一条预算，永远得到同一个标识和同样的字节——重编一次是有成本的，这个标识就是用来跨请求把这份成本省下来的。

### 收据上绝不放什么

```mermaid
flowchart TD
    R["一张收据"] --> Y1["放：不透明标识"]
    R --> Y2["放：格式、字节数、宽高"]
    R --> Y3["放：一个只供显示的名字"]
    R -.->|"绝不放"| N1["文件路径"]
    R -.->|"绝不放"| N2["带凭证的签名地址"]
    R -.->|"绝不放"| N3["图片字节本身"]
    N1 -.->|"收据会跟着日志落盘、还会送到客户端<br/>一旦它是路径或钥匙<br/>一份历史记录就等于一把长期有效的钥匙"| N2
```

那个显示名同理：它来自浏览器或者别处，是不可信输入，**只用来显示，绝不参与任何路径解析**。

### 契约和实现是怎么分家的

DSH 那边这是一个抽象类：四个抽象成员留给子类填，三个已经写好的方法子类继承就有。Go 没有实现继承，接口里也放不下方法体，所以这里把两半拆开：

```mermaid
flowchart LR
    subgraph C["契约那一半：一个接口"]
        C1["这个部署的限额是多少"]
        C2["验一张图"]
        C3["提交一张图"]
        C4["取回一张图"]
    end
    subgraph F["规矩那一半：三个包级函数"]
        F1["整批怎么验"]
        F2["一批图按什么次序提交"]
        F3["请求版本怎么要"]
    end
    F --> C
    F -.->|"比继承更硬：<br/>继承来的方法子类能覆盖掉<br/>包级函数覆盖不了"| F
```

这么分的理由是「一批图怎么排队校验和提交」和「字节存在哪儿」是两件独立变化的事，而**前者一旦写错，代价是脏数据**。把它钉在契约上，任何实现方都绕不过去。

## 一批图的次序，这是整篇里最要紧的一段

一条消息可以带好几张图。操作者的期望是很朴素的：**要么这条消息整条发出去，要么整条不发**。

```mermaid
flowchart TD
    subgraph BAD["边验边写"]
        A1["第一张：验过，写进去了"] --> A2["第二张：验过，写进去了"]
        A2 --> A3["第三张：不合格，整条消息发不出去"]
        A3 --> A4["前两张已经在存储里了<br/>而且永远不会被任何消息引用"]
        A4 --> A5["两块没人认领、又不敢删的字节"]
    end
```

```mermaid
flowchart TD
    subgraph GOOD["先把整批验完，再动第一次写"]
        B1["整批规矩：几张、加起来多大、什么格式"] --> B2["逐张验：真解一遍"]
        B2 --> B3{"全都过了吗"}
        B3 -->|"有一张没过"| B4["一次写都没发生"]
        B3 -->|"都过了"| B5["按输入顺序逐张提交"]
    end
```

### 写这一段没有事务，所以退一步说实话

```mermaid
flowchart LR
    A["写到第三张的时候存储出故障"] --> B["前两张确实已经在存储里了"]
    B --> C["这一层不假装能回滚"]
    C --> D["它保证的是另一件事：<br/>一个部分成功的批次不返回任何收据"]
    D --> E["没有收据就没人指得着它们<br/>那些字节等保留策略来收"]
```

**能给的保证要给足，给不了的不许含糊。** 说得出「回滚了」而实际上没回滚，比老实说「有残留但没人指得着」坏得多。

### base64 只认一种写法

上传进来的是 base64 文本。这里不接受「能解出来就行」，只认**规范形**：空串、带换行、填充不对、以及网址安全的那套别名，一律拒。

```mermaid
flowchart TD
    A["同一张图，编码时多打了一个换行"] --> B{"宽松解码"}
    B -->|"照样解得出来"| C["同样的字节，两种线上写法"]
    C --> D["「这条请求和那条请求是不是同一张图」<br/>取决于有没有人多敲了一下回车"]
    D --> E["而去重、缓存、配额全压在这个判断上"]
    F["收紧到只认一种写法"] --> G["这件事退化成一次字节比较"]
```

DSH 那边的做法是解完再编回去和原串比，因为它所在的运行时解码器极其宽松。Go 的严格解码器一趟就能拒掉绝大部分，只差两处，所以这里另外补两条显式检查：空串（一张零字节的图不是图），以及回车换行（Go 的解码器为了读分行编码，有意忽略这两个字符）。

## 落地那一台：字节的哈希就是它的名字

`adapter/imagestore` 是收据这条契约在本仓库的实现。它建在文件系统那条接缝上，所以服务端部署下面接的是对象存储——**换介质是装配时的一行事，不是改代码**。

它的办法叫内容寻址：

```mermaid
flowchart TD
    A["一张图的字节"] --> B["算一个哈希"]
    B --> C["这个哈希既是收据上的标识<br/>也是它在介质上的落点"]
    C --> D["同一张图，无论谁传、传几次<br/>算出来的都是同一个落点"]
```

### 存第二次会发生什么

```mermaid
flowchart TD
    A["要写这个落点"] --> B{"落点上有东西吗"}
    B -->|"没有"| C["写进去，发收据"]
    B -->|"有"| D["把已经在的那份读回来，重算哈希"]
    D --> E{"一致吗"}
    E -->|"一致"| F["同一张图，直接发收据<br/>这就是去重"]
    E -->|"不一致"| G["介质坏了或者被人动过<br/>报「已损坏」"]
    G -.->|"绝不覆盖，也绝不假装写成功"| G
```

**同一张图存多少次都只占一份**——第二次写自然撞到同一个落点，于是塌成一次核对。这不是特意做的去重逻辑，是内容寻址白送的。

DSH 那边为了在本机磁盘上自己保证发布的原子性，用了「临时文件加硬链接再同步目录项」那一整套。这条接缝上不需要：接缝本身就有一个「不覆盖地发布」的原语，原子性由介质那一侧负责。

### 存储里绝不放第二份描述

```mermaid
flowchart LR
    subgraph BAD["再存一个伴生的描述文件"]
        A1["对象 A：字节"] --- A2["对象 B：宽高、格式、字节数"]
        A1 -.->|"它们迟早会不一致"| A2
        A2 --> A3["而不一致的时候<br/>没有任何办法知道哪一份是对的"]
    end
```

```mermaid
flowchart LR
    subgraph GOOD["只存字节，描述在收据上"]
        B1["存储里只有字节"] --> B2["宽高、格式、字节数<br/>全在会话日志里那张收据上"]
        B2 --> B3["读回时重新算一遍再逐项核对"]
        B3 --> B4["哈希自己就是判据<br/>不需要第二个权威"]
    end
```

### 取回一张图要过三道

```mermaid
flowchart TD
    A["调用方交回一张收据"] --> B["① 收据本身长得对不对<br/>标识必须是那个固定形状"]
    B --> C["② 按收据记的字节数为上限去读<br/>读到更长的，说明那份已经坏了"]
    C --> D["③ 重算哈希，和标识比"]
    D --> E["④ 重认一遍文件头<br/>格式、字节数、宽、高，逐项和收据比"]
    E --> F["全对上：这些字节就是当初存进去的那些"]
    D -.->|"改一个 bit 就读不出来<br/>这是「收据描述的还是这些字节」唯一的证据"| D
```

取回时**不再把整张栅格解一遍**：哈希对上就证明这些字节正是准入时完整解过的那些，而历史回放会一遍遍走这条路，多解一次是白花的力气。

### 六条限额，分两个地方判

```mermaid
flowchart TD
    L["部署配的六条限额"] --> S["接缝上就能判的三条<br/>光看输入不用解码"]
    L --> D["必须把图解出来才知道的三条"]
    S --> S1["一条消息最多几张"]
    S --> S2["一条消息里加起来最多多大"]
    S --> S3["这个部署收哪几种格式"]
    D --> D1["单张最多多大"]
    D --> D2["最多多少像素"]
    D --> D3["单边最长多少"]
    D -.->|"用哪个解码库是实现方的选择<br/>所以这三条不写死在契约里"| D
```

同时犯了好几条的时候，报出去的是**最外层那条**：

```mermaid
flowchart LR
    A["一批 30 张图，其中第七张格式不对"] --> B["报的是「你传得太多了」"]
    B --> C["因为那句话更接近<br/>操作者要做的下一个动作"]
    D["报「第七张的格式不对」"] -.->|"他删到 20 张之后还会再撞一次墙"| C
```

### 光看文件头不够

```mermaid
flowchart LR
    A["只读文件头"] --> B["查得出格式和宽高"]
    A --> C["查不出后面那段字节是不是截断的、是不是坏的"]
    C --> D["一张头部完好、数据段坏掉的图<br/>会一路存进去"]
    D --> E["直到某个模型提供方<br/>在很远的地方解不开它"]
    F["所以准入时把栅格整个解出来一遍<br/>只为证明它解得开"] --> E
```

### 显示名要剥干净

```mermaid
flowchart LR
    A["客户端交上来<br/>一整条本机路径"] --> B["两种分隔符都手工剥掉<br/>只留最后那一节"]
    B --> C["去掉控制字符，去掉首尾空白"]
    C --> D["超长就截断<br/>但不切开一个多字节字符"]
    D --> E["剥空了就是「没有名字」"]
    F["靠本机的路径规则去取叶名"] -.->|"交名字上来的客户端<br/>和这台服务不是同一套规则"| B
```

切开一个多字节字符的后果不是「显示难看」——那个半截字符会跟着收据一路落盘。

### 本轮画出来的三条边界

这三件事**不做，是决定，不是遗漏**：

```mermaid
flowchart TD
    N1["不做归一化缩放"] --> R1["缩放要一个编码器<br/>本轮不把它带进来"]
    R1 --> C1["后果：存下来的就是<br/>操作者传上来的那些字节"]
    N2["不派生请求版本"] --> R2["同样要编码器"]
    R2 --> C2["后果：调用方拿到一个明确的<br/>「这个实现不支持」"]
    N3["不认 EXIF 旋转"] --> R3["这里没有 EXIF 解析器"]
    R3 --> C3["后果：收据上记的是栅格自己的宽高<br/>那段 EXIF 原样留在字节里<br/>渲染方照旧转得过来"]
```

第二条之所以能这么干净地留白，是因为「派生请求版本」在契约上就是**可选能力**：实现方具备就走它，不具备就得到一个固定的失败码。不必为了「我不支持」去写一个只会报错的方法。

```mermaid
flowchart TD
    A["调用方要一份请求版本"] --> B{"挂着的这台存储<br/>具备这个能力吗"}
    B -->|"具备"| C["按预算派生一份"]
    B -->|"不具备"| D["「这个实现派生不出请求版本」"]
    D -.->|"是一句明确的话<br/>不是一次崩溃，也不是一张凑合的图"| D
```

## 生命周期与并发

```mermaid
flowchart TD
    A["这两个包都不持有后台协程"] --> B["也不持有任何可变状态"]
    C["并发安全由介质那一侧负责"] --> C1["「不覆盖地发布」由后端保证"]
    D["同一批字节的标识必须稳定"] --> D1["同一份派生的标识也必须稳定"]
    D1 -.->|"否则缓存和上传索引会各自为政"| D1
    E["交出去的限额是一份拷贝"] --> E1["这几条在一台存储的一生里不许变"]
    E1 -.->|"整批先按它判过、再逐张写<br/>中途变化会让两段按两套规矩走"| E1
```

对象一旦提交就是不可变的：没有「原地改一张图」这个动作，改了就是另一张图、另一个标识。**保留多久、要不要加密，归介质那一侧的策略管**，这两个包不表态。

## 失败语义

所有失败都带一个稳定的机器码，调用方**照码分派，绝不去匹配错误文字**。这些码是线上可见的，所以取值一律照 DSH 原样落地，不改拼写、不本地化。

```mermaid
flowchart TD
    A["出了岔子"] --> B{"谁能让下一次尝试成功"}
    B -->|"调用方自己"| C["图片准入类<br/>张数超了、总量超了、格式不收、<br/>base64 不规范、解不出是图、<br/>声称的格式和字节对不上、<br/>单张太大、像素太多、边太长"]
    B -->|"谁也不能，得修系统"| D["存储故障类<br/>收据不合法、已损坏、<br/>写失败、找不到、读失败、<br/>派生能力不具备"]
    C --> C1["界面提示操作者换一张图"]
    D --> D1["界面报一次系统故障"]
```

这条分界线上有一个**故意的偏向**：

```mermaid
flowchart LR
    A["一个判不出类别的错误"] --> B["一律当成存储故障"]
    C["反过来：把存储故障说成「你的图不行」"] -.->|"操作者会反复换图<br/>而问题根本不在他那边"| B
```

### 一条不显眼但要紧的次序

```mermaid
sequenceDiagram
    participant U as 调用方
    participant A as 附件层
    U->>A: 要一份请求版本
    Note over U: 这时候调用方自己已经走了<br/>（超时、取消、连接断了）
    A-->>U: 报「这次调用已取消」
    Note over A: 而不是报「这个实现不支持派生」
```

**取消优先于「不支持」。** 调用方已经不在了的时候，「这台实现具备不具备某项能力」根本不是它要知道的事——报「不支持」只会让日志里出现一条其实从没被真正需要过的能力缺口。

### 错误码不靠继承传递

```mermaid
flowchart LR
    A["别的包里的错误"] --> B["只要它答得出自己的码<br/>就照样按码分派"]
    B --> C["它不需要引用附件这个包"]
    C -.->|"因为模型消息那一层已经引用了附件的收据<br/>反过来再引一次就成环了"| C
```

判断还会**顺着包装链一路往下问**，而不是只看最外面那一层——在 Go 里包一层错误是常态，只看最外层等于让「谁顺手包了一下」决定这个判断的结果。

## 能力边界

```mermaid
flowchart TD
    Y["做的"] --> Y1["一套谁都绕不过去的准入与提交次序"]
    Y --> Y2["一张能进会话日志、也能送客户端的收据"]
    Y --> Y3["内容寻址：去重和完整性是同一件事"]
    Y --> Y4["一组稳定的失败码，分得清「换张图」和「修系统」"]
    N["不做的"] --> N1["不是文件系统<br/>没有路径、目录、列举、原地编辑<br/>只有「提交」和「按收据取回」两个动作"]
    N --> N2["不做图片编解码<br/>只解开来验一验，不重新编码"]
    N --> N3["不判断某条模型路由收不收图<br/>那是模型路由那一层的事"]
    N --> N4["不做事务，也不清垃圾<br/>没人引用的对象归介质的保留策略收"]
    N --> N5["不管保留期，也不管加密"]
```

最后补一句最容易被误会的：**附件不是网盘。** 它只认「提交一次、以后凭收据取回」这一种用法，而且提交进去的东西再也不会变。任何需要「改一改再存回去」的场景，答案都是另存一张新的。
