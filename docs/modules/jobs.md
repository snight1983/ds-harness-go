# 后台作业

对应包：`feature/jobs`、`feature/jobs/jobstool`、`adapter/localjobs`、`adapter/domainjobs`

## 定位

有些活儿一句话干不完：跑一个几分钟的构建、开一个长连着的进程、拉一份很大的数据。模型不能就这么杵在那儿等——它得**把活儿放到后台**，先去干别的，等干完了再回头看一眼。

```mermaid
flowchart LR
    subgraph N["没有后台作业"]
        A1["模型说：跑构建"] --> A2["等……"] --> A3["等……"] --> A4["八分钟后拿到结果<br/>这中间它什么都干不了"]
    end
```

```mermaid
flowchart LR
    subgraph Y["有后台作业"]
        B1["模型说：跑构建"] --> B2["拿到一个作业号，接着干别的"]
        B3["构建自己在后台跑"] --> B4["跑完了"]
        B4 --> B5["回头通知模型一声"]
    end
```

这几个包管的是那个**作业号**，以及围着它的四件事：谁看得见、怎么读、怎么停、跑完了怎么说一声。

**它们不跑那件活儿。** 起协程、干活、结算，全是生产方自己的事。

---

## 架构

```mermaid
flowchart TD
    PROD["生产方<br/>（真正干活的那一侧）"] -->|"Start ＋ 三个钩子"| REG["作业注册表"]
    REG --> IMPL{"两台实现挑一台"}
    IMPL --> L["localjobs<br/>账本在进程内存"]
    IMPL --> D["domainjobs<br/>账本在数据库的一张域表"]
    REG --> TOOL["jobstool<br/>job_list / job_output / job_kill"]
    TOOL --> M(("模型"))
    REG -->|"跑完了"| NOTE["通知投回属主 agent"]
    NOTE --> M
```

四个包的分工：

| 包 | 它管的 | 它明确不管的 |
|---|---|---|
| `feature/jobs` | 契约：作业号、可见性、生命状态、结算广播 | 谁去跑、跑在哪儿 |
| `adapter/localjobs` | 单进程里的一本账 | 别的副本 |
| `adapter/domainjobs` | 一本所有副本都读得到的账 | 把执行资源也共享出去 |
| `feature/jobs/jobstool` | 模型这一侧的三件工具、以及跑完了怎么惊动模型 | 作业本身 |

## 一件作业的一生

```mermaid
stateDiagram-v2
    [*] --> running: Start（先落账，再开跑）
    running --> stopping: Kill（请求取消）
    running --> done: 生产方自己结算
    stopping --> done: 生产方响应了取消
    stopping --> failed: 取消钩子自己炸了
    running --> failed: 生产方报了失败
    done --> [*]
    failed --> [*]
```

### 结算只发生一次

```mermaid
flowchart TD
    A["第一个到达的结算"] --> B["① 写下终态记录"]
    B --> C["② 放掉所有等着的人"]
    C --> D["③ 挨个通知观察者<br/>每个都裹一层，一个炸了不带倒别人"]
    D --> E["④ 最后才告诉属主 agent「跑完了」"]
    F["后到的结算"] -.->|"丢弃"| A
```

**为什么「告诉属主」要排在最后**：那一步可能当场开一个模型回合。排在前面的话，模型会在别的观察者还没看到这件事、终态记录还没写完的时候就开始动。

### Kill 是请求，不是保证

```mermaid
sequenceDiagram
    participant M as 模型
    participant R as 注册表
    participant P as 生产方
    M->>R: job_kill
    R->>P: 调它的取消钩子
    R-->>M: 「已请求取消」
    Note over P: 守规矩的：收手，结算<br/>不守规矩的：接着跑，没人能掐死它
```

Go 没有掐死别人协程的办法。所以这里如实说「请求了」，而不是把「已请求取消」说成「已经停了」。

## 两台实现，按部署形态挑

```mermaid
flowchart LR
    subgraph LOC["localjobs"]
        L1["账本：进程内存"]
        L2["别的副本：看不见"]
        L3["进程重启：记录全没"]
    end
    subgraph DOM["domainjobs"]
        D1["账本：数据库的一张域表"]
        D2["别的副本：看得见"]
        D3["进程重启：记录还在<br/>盖着自己名字还挂着的，判成失败"]
    end
```

两台在装配面上对着换。多副本部署下用 `localjobs` 的后果：

```mermaid
flowchart TD
    A["A 副本起了一件作业"] --> B["在 B 副本上列举"]
    B --> C["少一行"]
    B --> D["终止它：「没有这件作业」"]
    C -.->|"两句都不是真话"| E["而调用方无从分辨"]
    D -.-> E
```

`domainjobs` 是本仓库自有的，DSH 那边只有一台进程内的实现——对一个桌面工具那是对的，对多副本部署不是。

## `domainjobs`：账本共享，执行不共享

理解它所有的分岔只需要这一条：

```mermaid
flowchart TD
    J["一件作业身上有两样东西"] --> R["它的记录<br/>id、种类、标签、属主、状态、结局"]
    J --> X["它的执行资源<br/>取消钩子、输出管道"]
    R --> RS["落在域表上<br/>任何副本任何时候都读得到"]
    X --> XS["只在起这件活儿的那个进程内存里<br/>序列化不了，也就搬不走"]
```

于是能力按副本分成两半：

```mermaid
flowchart LR
    A["List / Get<br/>（只用得着记录）"] --> A1["每个副本答案一致"]
    B["Read 实时输出 / Kill<br/>（用得着执行资源）"] --> B1{"我是执行它的那个副本吗"}
    B1 -->|"是"| B2["办"]
    B1 -->|"不是"| B3["报错，并点名它跑在哪个副本上"]
    B3 -.->|"绝不假装成功"| B4["一个调用方以为自己停掉了一件还在跑的活儿<br/>比一句「这儿办不了」坏得多"]
```

### 记录先于活儿

```mermaid
flowchart LR
    subgraph BAD["先跑再落账"]
        A1["开跑"] --> A2["这中间进程没了"] --> A3["一件跑着的活儿<br/>在账本上不存在"]
    end
```

```mermaid
flowchart LR

```

两种残留都可能发生，但**只有后一种是收得回来的**。

## `jobstool`：模型那一侧，以及跑完了怎么惊动它

### 装工具的同时把控制器也接上

```mermaid
flowchart LR
    A["装 jobstool"] --> B["① 三件工具进模型的工具表"]
    A --> C["② 控制器接到这个属主上"]
    B -.->|"故意合成一次装配动作"| C
    C --> D["「谁读得到作业」和「谁起得了作业」<br/>永远是同一个答案"]
```

### 跑完了：属主忙就注入，属主闲就唤醒

```mermaid
flowchart TD
    A["一件作业结算了"] --> B{"属主 agent 此刻在干活吗"}
    B -->|"在忙"| C["注入：那条通知在它下一步的收件箱里等着"]
    B -->|"闲着"| D["唤醒：开一步，把通知递进去"]
    C --> C1["好处：一堆作业同时完，只花一步"]
    D --> D1["必须唤醒的理由：一条没人认领的通知<br/>＝ 一次模型永远不知道的完成"]
```

### 自激唤醒链要有闸

```mermaid
flowchart LR
    A["唤醒开了一步"] --> B["这一步里又起了一件作业"] --> C["它又完了，又唤醒一步"] --> A
    D["连续唤醒预算"] -.->|"到数就不再唤醒"| A
    E["一条人写的输入被认领"] -.->|"预算清零"| D
```

**为什么人的输入能清零**：链条是模型自己烧出来的；人重新说了一句话，说明这不是自激，是有人在看着。

### 两张记账用的映射

```mermaid
flowchart TD
    subgraph M1["按 agent 记：连续唤醒了几次"]
        A1["键：agent"] --> A2["清理挂在这个 agent 自己的作用域上"]
    end
    subgraph M2["按这次工具执行记：这一次的上下文"]
        B1["键：工具执行令牌"] --> B2["在结果规范化那一步删掉<br/>那一步每次执行恰好走一遍"]
    end
    LOCK["两张共一把互斥锁"] --> M1
    LOCK --> M2
    LOCK -.->|"因为结算来自生产方的协程<br/>而工具调用来自模型那一侧"| LOCK
```

DSH 那边这三处用的是 `WeakMap`，靠垃圾回收顺手清掉。Go 没有这个东西，所以清理点必须写明白——挂在作用域上，或者挂在一个恰好走一次的调用上。

## 能力边界

```mermaid
flowchart TD
    Y["这几个包做的"] --> Y1["发号、圈可见范围、记状态、广播结算"]
    Y --> Y2["把完成这件事送到模型面前"]
    N["不做的"] --> N1["不是任务队列<br/>没有排队、没有重试、没有跨副本调度"]
    N --> N2["不起协程<br/>活儿归生产方自己拥有"]
    N --> N3["Kill 是协作式取消<br/>不是强杀进程"]
    N --> N4["完成通知是副本本地的<br/>B 副本结算的作业唤不醒 A 副本上的 agent"]
    N --> N5["domainjobs 的终态记录一直留在表上<br/>谁来清、留多久，本轮没有答案"]
```

后两条各补一句：跨副本唤醒要补得有一套发布订阅，本轮不做；而终态记录之所以不敢顺手删，是因为**那是别的副本唯一还能读到结局的地方**。
