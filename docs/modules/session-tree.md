# 会话日志与派生状态（`sessionlog/`）

本文讲会话日志这一条线：事件词汇，加上围着它转的九个包。这九个包分住在 `sessionlog/projection`、`feature/` 和 `adapter/` 三处，所以本文按职责编排，不按目录编排。活会话对象和会话检索不在本文范围内，只在需要说明接缝时点到名字。

```mermaid
flowchart LR
    P["产品 / 设计"] --> P1["定位整节<br/>架构里的全景与三级读法<br/>失败语义的判定图"]
    D1["研发：要改这棵树"] --> D2["全文"]
    D3["研发：只是用它"] --> D4["架构<br/>装配顺序<br/>失败语义"]
```

## 定位

### 为什么需要这棵树

一次会话里发生过的事，如果只活在内存里，那么进程一没，它就等于没发生过。

```mermaid
flowchart LR
    subgraph BAD["只把会话记在内存里"]
        A1["模型请求发出去<br/>钱开始花"] --> A2["工具跑起来<br/>文件被写了"]
        A2 --> A3["崩溃"]
        A3 --> A4["重新打开<br/>这两件事一件都不在"]
        A4 -.->|"世界上真的发生过<br/>但没人记得"| A1
    end
```

```mermaid
flowchart LR
    subgraph GOOD["每一个撤不回来的动作之前，先把日志按进耐久介质"]
        B1["要发模型请求<br/>要跑工具"] --> B2["先把已经记下的那一段<br/>刷到耐久为止"]
        B2 --> B3{"刷得下去吗"}
        B3 -->|"刷得下去"| B4["放行<br/>动作跑出去"]
        B3 -->|"刷不下去"| B5["整条路断掉<br/>宁可这次做不成"]
    end
```

这棵树回答的就是这一件事：**一次会话里发生过什么，怎么记下来、怎么存住、怎么读成能用的东西。**

### 产品在界面上看到的四件事

```mermaid
flowchart LR
    U1["新会话立刻有个名字<br/>过一会儿换成更像样的<br/>你改过就再也不动"] --> T1["标题那两个包"]
    U2["会话详情里的几个数字<br/>怎么翻页怎么压缩都不变"] --> T2["会话数字"]
    U3["会话列表秒开<br/>不用把历史读一遍"] --> T3["折叠进度缓存"]
    U4["断电崩溃强杀之后<br/>已经花过的钱一件不少"] --> T4["耐久屏障"]
```

第四条是这棵树存在的根本理由。模型请求一发出去钱就开始花、回答也开始在世界上存在；工具一跑起来文件就被写了、请求就被发了。这些事撤不回来。

```mermaid
    Q3["读成什么"] --> A3["折成当前状态<br/>并把折叠进度存住"]
```


### 一条贯穿全树的原则


## 架构

### 全景

```mermaid

        Title["会话标题"]
        Tele["外发上报"]
    end

    Live -->|"追加一条"| Event
    Live --> Policy
    Policy -->|"刷到耐久为止"| Coord
    Live -->|"事件已提交"| Coord
    Coord --> WB
    WB --> Backend
    Backend --> PG
    Backend -.-> Other

    Live -->|"推进"| Reg
    Reg --> Stats
    Reg --> Title
    Reg --> Cache
    Cache --> Domain[("另一条写链<br/>存储域")]
    Live -->|"观察"| Tele

    Rules -.被两侧共用.-> Reg
```

**图怎么看**：中间那个活会话是发动机，它不在本文范围内，但每一条线都从它出发。往左下是写，往右下是读。最上面那层是词汇——它只有值和纯函数，写侧读侧都用它，但它谁也不认识。

```mermaid

    subgraph BAD2["把介质焊死在编排层里"]
        X1["编排层直接写数据库"] --> X2["换介质要改编排层"]
        X2 -.->|"而这个仓库是一个空运行时<br/>介质本来就该由装配方挑"| X1
    end
```

```mermaid
flowchart LR
    subgraph GOOD2["编排层只认一道缝"]
        Y1["编排层"] --> Y2["缝：把一批事件写下去、读回来、列举"]
        Y2 --> Y3["仓库自带的那一个：<br/>一个会话就是一条流"]
```

DSH 那两个第一方介质在裁决表里是不做，没有移过来；仓库自带的只有一个。数据库那一摊整个收在持久化适配层底下，这条界线由仓库的数据库门禁把着。

### 两条写链，一条次序

```mermaid
flowchart LR
    E["一条事件"] --> L1["会话日志<br/>走落地接缝"]
    E --> P1["折进各个单元"]
    P1 --> K1["折叠进度<br/>走存储域"]
    L1 -.->|"必须先落<br/>缓存可以落后于日志，不能领先"| K1
```

两条链各写各的介质，不要求同一个。唯一的约束是那条虚线。为什么：

```mermaid

        Z2 --> Z3["从任何已存日志都推不出它"]
        Z3 --> Z4["而它带着一个看起来完全正常的水位"]
        Z4 --> Z5["堂堂正正地被端给客户端"]
    end
```

### 一条事件的一生

```mermaid
sequenceDiagram
    participant L as 活会话
    participant P as 耐久屏障
    participant C as 编排层
    participant R as 折叠注册表
    participant K as 折叠进度缓存

    Note over L,P: ① 要发模型请求 / 要调工具 / 要开新步骤
    L->>P: 钩子触发
    P->>C: 同步等它落地
    alt 刷不下去
        P-->>L: 报错，后面一步都不许走
    else 刷成功
        P-->>L: 放行
    end

    Note over L: ② 事件产生并追加进日志
    L->>C: 事件已提交
    C->>C: 攒一批
    L->>R: 同步折进所有单元
    R->>R: 上一个状态 + 这条事件 = 新状态
    L->>K: 观察一下
    alt 回合结束 / 攒够 / 到点
        K-->>K: 异步写进度，失败只记一行
    end
```

```mermaid
flowchart LR
    A["① 发生之前拦住"] --> A1["刷不下去就整条路断掉<br/>宁可这次做不成"]
    B["② 提交之后跟进"] --> B1["失败了只是下次读的时候慢一点"]
    A1 --> C["关门的在前面<br/>尽力而为的在后面"]
    B1 --> C
```

### 三级读法

同一份状态有三条读路径，代价递增：

```mermaid
flowchart LR
    A["走活会话<br/>内存，零读写"] --> A1["实时界面<br/>当前请求"]
    B["只看已经存下的进度<br/>零读写，值可能旧"] --> B1["列表页"]
    C["存下的进度 + 日志尾巴<br/>读一截，折完写回"] --> C1["点开一个冷会话"]
    D["整读<br/>从存档现存的最前面"] --> D1["缓存作废时的兜底"]
    A -.->|"越往右越贵"| B
    B -.-> C
    C -.-> D
```

产品视角上这就是「为什么列表页秒开、点进去要转一下圈」：列表页走第二级，点进去走第三级。

阶梯往下退是设计内的：

```mermaid
stateDiagram-v2
    state "第二级：只看存下的进度" as L2
    state "第三级：进度 + 日志尾巴" as L3
    state "整读：从现存最前面重折" as L4
    L2 --> L3 : 要实时的值
    L2 --> L4 : 缓存缺失 / 版本变化
    L3 --> L4 : 绑到了另一段日志 / 日志被崩溃修复截过尾
    L4 --> L2 : 折完写回，下次起点更近
```

```mermaid
flowchart LR
    A["任何一级的底线"] --> B["一个值可能旧"]
    A --> C["绝不可能错"]
    C -.->|"这一条是整个读侧的底线"| B
```

## 十个单元各管什么

### 依赖全貌

```mermaid
flowchart TB
    subgraph mech["机制：这套东西本身"]
        direction TB
        V["词汇层"]
        PE["落地接缝 + 编排"]
        PG2["仓库自带的唯一介质"]
        CP["耐久屏障"]
        PJ["折叠机制"]
        PC["折叠进度存住"]
    end

    subgraph use["使用者：拿机制干活"]
        direction TB
        ST["会话数字"]
        TI["会话标题"]
        TL["拿模型起标题"]
        TE["外发上报"]
    end

    PE --> V
    PG2 --> PE
    CP --> PE
    PJ --> V
    PC --> PJ
    PC --> PE
    ST --> PJ
    TI --> PJ
    TL --> TI
    TE --> PJ
```

箭头是「谁依赖谁」。词汇层在最底下，谁都可以用它，它谁都不用——这是它能只放值和纯函数的原因。自带的那个介质是接缝的**使用者**而不是它的一部分，装配方自己写的介质站在同一个位置。右边那一列全部只依赖折叠机制，它们随时可以整个不装。

一张表看完十个单元的能力和它最要紧的那条边界：

| 单元 | 能力一句话 | 最要紧的一条边界 |
|---|---|---|
| 词汇层 | 事件长什么样、日志立不立得住 | 不持有任何活对象 |
| 落地接缝 + 编排 | 那道缝 + 按会话串行的编排 | 不是具体介质 |
| 自带的那个介质 | 一个会话一条流，接到日志集上 | 没有逐字节原始存档，也不认路 |
| 耐久屏障 | 三处副作用边界上的屏障 | 只喊「现在刷」，不判断「有没有东西要刷」 |
| 折叠机制 | 事件折成当前状态 | 只提供机制，不提供内容 |
| 折叠进度 | 进度落地 + 两级带介质读 | 永远不是权威，随时可以整个丢掉 |
| 会话数字 | 从整份日志折出那几个数 | 数步骤收尾事件，不数装配好的助手消息 |
| 会话标题 | 标题状态与三种来路 | 不缓存任何标题，每次从日志现折 |
| 拿模型起标题 | 一次辅助模型调用的全部策略 | 只收一个窄接口，不收整个模型运行时 |
| 外发上报 | 上报的采集侧 | 交出去之后的那一段一个字都不建模 |

### 词汇层

它就是那份共识——所有人都得对「一条会话记录长什么样」有一致的理解，否则写的人和读的人对不上。而且它只是共识，它不干活。

```mermaid
flowchart TB
    V["词汇层做四件事"] --> V1["定义一条日志条目：<br/>序号 · 时间 · 类型 · 负载<br/>十三种具名负载 · 会话头 · 会话身份"]
    V --> V2["判一份日志立不立得住：<br/>序号 · 回合与步骤配对 · 工具调用配对<br/>读到不认识的类型怎么办"]
    V --> V3["把一份崩在半路的日志<br/>补齐成模型提供方肯收的历史"]
    V --> V4["把日志折成模型可见历史"]
```

事件负载**故意不解成联合类型**：

```mermaid
flowchart LR
    subgraph BAD4["解成一个封闭联合"]
        A1["DSH 的事件登记表有 48 个类型<br/>本仓库实现其中 13 个"] --> A2["读到第 14 种"]
        A2 --> A3["解成「未知」"]
        A3 --> A4["排回去时把它的字段丢掉"]
        A4 -.->|"而日志是持久的<br/>丢掉的是别人写下的历史"| A2
    end
```

```mermaid
flowchart LR
    subgraph GOOD4["负载就是一段原始字节"]
        B1["读到不认识的类型"] --> B2["原样保管那段字节"]
        B2 --> B3["需要具名字段时才按需解一次"]
    end
```

因此「解不开」不等于「日志失败」，那是两件事：

```mermaid
flowchart TD
    E["读到一条事件"] --> Q{"本构建认识这个类型吗"}
    Q -->|"认识"| OK["按具名字段用"]
    Q -->|"不认识"| Q2{"这条标了可跳过吗"}
    Q2 -->|"标了"| SKIP["放过，原样保管字节"]
    Q2 -->|"没标"| REJ["拒的是整份日志"]
    REJ -.->|"一条不认识的必需事件<br/>可能改变后面整段日志的解释方式<br/>静默跳过等于重建出一个错的会话"| REJ
```

它还有一条边界：**不解释业务含义**。它知道一条「要调这个工具」后面该配一条「工具给了什么」，不知道那个工具干了什么。拆出来单放一个包的理由是落地那一层只需要值和纯函数，混在一起它就得连着一整套用不到的东西一起立起来。

### 落地接缝与编排

```mermaid
flowchart TB
    L3["第三层：编排<br/>按会话身份串行化每次操作<br/>挂在会话存储的四条观察者上<br/>认领活会话 · 维护准备池 · 编排崩溃修复 · 关闭时排干"] --> L2["第二层：攒批控制器<br/>不认识会话，只认识<br/>「攒一批、到点写下去、写失败了把缓冲留着」"]
    L2 --> L1["第一层：词汇与纯函数<br/>介质的最小原始能力集 · 使用方的服务面<br/>跨介质的那几种值 · 三道判据 · 把中断的日志补平 · 认领时那道判据"]
```

介质的四项可选本事由类型探测发现，有就用、没有就退回慢做法：按序号直接寻址、可关闭、可从最老一头弹掉、能指出一份逐字节的原始存档。

**四条边界**：

```mermaid
flowchart TD
    N["这一层不做什么"] --> N1["不是具体介质<br/>它给出的是那道缝"]
    N --> N2["不解释模型、工具或业务事件的业务含义"]
    N --> N3["不做格式迁移<br/>格式版本在未发布期间钉在 0<br/>不承诺兼容性，不匹配的日志直接拒收"]
    N --> N4["不看断尾凭据"]
    N3 -.->|"既然不迁移<br/>就没有旧形状要升级"| N3
```

断尾凭据这一条值得单说：

```mermaid
flowchart LR
    A["介质说：后面还挂着一截写坏的尾巴"] --> B["凭据的类型是「任意」"]
    B --> C["编排层唯一会做的事<br/>就是把它原样递回给那个介质"]
    C -.->|"「任意」这个类型<br/>表达的正是「不看」这件事本身"| B
```

这一层也不替代所有消费方接口：宿主仍需提供生产介质、把服务面注入会话存储、装上编排层，并为 agent 循环适配准备池的发布与释放。

### 仓库自带的那一个介质

```mermaid
flowchart LR
    S1["一个会话"] --> S2["就是一条流"]
    A1["会话身份"] --> A2["流名"]
    B1["会话头"] --> B2["流的头"]
    C1["一条事件"] --> C2["一条条目"]
    D1["事件的序号"] --> D2["条目的序号"]
    S2 -.->|"本包里没有一句 SQL、没有一个连接池<br/>那些全在持久化适配层底下<br/>它只做翻译"| S2
```

四项可选本事它满足其中三项：

```mermaid
flowchart TD
    Y["满足"] --> Y1["按序号直接寻址<br/>在日志集上是走主键的一句读<br/>不必像顺序介质那样先把前面全解一遍"]
    Y --> Y2["可关闭"]
    Y --> Y3["可从最老一头弹掉一段"]
    N["不满足"] --> N1["指出一份逐字节的原始存档"]
```

### 耐久屏障

它自己一行状态都不存，装上去之后只做一件事：在「这一步的后果将要跑到会话日志管不着的地方去」之前，先把日志已经记下的那一段刷到耐久为止。

```mermaid
flowchart LR
    subgraph inside["会话日志管得着的世界"]
        S1["追加事件<br/>随时可以重来"]
    end
    B1{{"屏障 ①<br/>模型请求派发前"}}
    B2{{"屏障 ②<br/>顶层工具调用派发前"}}
    B3{{"屏障 ③<br/>每个步骤开始前"}}
    subgraph outside["管不着的世界：撤不回来"]
        O1["模型开始出字<br/>钱开始花"]
        O2["写文件 · 发请求 · 跑命令"]
        O3["下一次请求"]
    end
    S1 --> B1 --> O1
    S1 --> B2 --> O2
    S1 --> B3 --> O3
```

| 边界 | 刷的是什么 | 为什么是这里 |
|---|---|---|
| 模型请求派发前 | 这次请求 | 一发出去钱就开始花，模型也开始产出。此后崩溃，恢复出来的会话缺掉这次请求，而它的回答已经在世界上存在过了 |
| 顶层工具调用派发前 | 「我要调这个工具」那条记录 | 工具体是唯一能改到会话之外的世界的地方：写文件、发请求、跑命令 |
| 每个步骤开始前 | **上一步**提交的那一批 | 放在下一步开头而非上一步结尾——一个步骤结尾未必有下文，而下一次请求一定有 |

装卸是一对：

```mermaid
flowchart LR
    A["一次挂齐三条"] --> B["返回一个把它们一起摘下来的函数"]
    A --> C{"中途装不上"}
    C --> D["按反序摘干净再报错"]
    D -.->|"半装上去比装不上更坏"| D
```

它做的唯一判断是「这次该不该我管」：

```mermaid
flowchart TD
    Q["一次钩子触发"] --> Q1{"认得出是哪个会话吗"}
    Q1 -->|"认不出"| P1["放过<br/>起标题、压缩摘要这类辅助调用<br/>不属于任何会话"]
    Q1 -->|"认得出"| Q2{"是嵌在别的工具调用里面的吗"}
    Q2 -->|"是"| P2["放过<br/>外层进来时已经刷过<br/>里面再刷是拿一次强制落地换不来任何新东西"]
    Q2 -->|"否"| GO["刷"]
```

```mermaid
flowchart TD
    N["它不做什么"] --> N1["只喊「现在刷」<br/>不判断「有没有东西要刷」"]
    N --> N2["不拥有存储介质"]
    N --> N3["不负责状态缓存的数量和时间节流"]
```

### 折叠机制

日志是流水账，界面要的是余额。这就是那台从流水账算余额的机器——而且是增量算的，来一条加一条。

```mermaid
flowchart LR
    E1["事件 n"] --> A1["折一次"]
    S0["状态停在 n-1"] --> A1
    A1 --> S1["状态推到 n"]
    A1 --> C{"变了吗"}
    C -->|"变了"| N["把新值通知出去"]
    C -->|"没变"| X["什么都不发"]
    C -.->|"「变没变」是显式返回的<br/>Go 没法像 JS 那样靠引用相等判断"| C
```

各个域只写这一个纯函数，框架负责订阅、逐会话记水位、值变了通知出去。域不持有任何订阅，也不知道谁在读；读的一方不知道值是怎么算出来的。

```mermaid
flowchart LR
    K1["折叠键"] --> K2["会话身份"] --> K3["单元格：状态 + 折到第几条"]
    K3 -.->|"内存里就是这两跳定位"| K1
```

对外四件事：登记（引用计数、注销幂等）、推进、读（三级）、出检查点。

**承重前提：整值事件规则。**

```mermaid

```

```mermaid

        B1["每次转移都便宜到可以无脑跑"] --> B2["每个被服务出去的值<br/>自己就说明了自己"]

```

检查点交出去的是**排出去的字节**，不是活引用：


### 会话标题

```mermaid
stateDiagram-v2
    state "没有名字" as S0
    state "兜底名：截第一条人类消息的前几个词" as S1
    state "模型起的名" as S2
    state "用户自己改的名：钉住" as S3
    S0 --> S1 : 用户发第一条消息，同步、确定、不花钱、立刻落地
    S1 --> S2 : 模型那一步异步跑完，顶掉兜底
    S1 --> S3 : 用户手动改名
    S2 --> S3 : 用户手动改名
    S3 --> S3 : 后续消息不再排期，在途的自动生成当场作废
    S3 --> S2 : 只有一条路解开：一次显式的刷新
```

兜底那一步是同步、确定性、不花钱的，所以列表行永远不会出现「无标题」；模型那一步是异步的，好了就顶掉；用户一改就钉死。

标题为什么必须是日志上的一条事件，而不是会话头上一个可以随手改的字符串：

```mermaid

    subgraph BAD10["存成会话头上一个可变字段"]

        A2 --> A3["换了模型、改了提示词之后<br/>就再也答不上来了"]
    end
```

```mermaid
flowchart TD
    subgraph GOOD10["当成日志上的一条事件"]
        B1["谁起的 · 从哪几句话起的 · 什么时候起的"] --> B2["全都写进去<br/>一条都不放在旁边的可变元数据里"]
        B2 --> B3["服务不缓存任何标题<br/>每次从日志现折"]
        B3 --> B4["进程重启后服务自己那份并发账从零开始<br/>而标题本身一个字都不会丢"]
    end
```

因此折出一份标题快照、以及把够格的消息收集出来，这两件事**不需要服务也不需要活会话**——一份回放出来的日志照样答得上话。


脱敏是一串显式规则，形状就是中间件那条链：

```mermaid
flowchart LR
    R0["原始记录"] --> R1["规则 1"]
    R1 -->|"往下走"| R2["规则 2"]
    R2 -->|"往下走"| R3["规则 3"]
    R3 --> S2["接收器"]
    R2 -.->|"不往下走：把后面的全部替换掉"| S2
```

每条规则拿到原始记录加一个「往下走」的入口，往下走就可以再加工返回来的东西，不往下走就把后面的整段替换掉。这是部署方唯一能改上报内容的地方。

交出去之后的那一段一个字都不建模——攒批、重试、排队、丢弃策略全都不在这里：

```mermaid
flowchart LR
    subgraph BAD12["把攒批和重试也收进采集侧"]
        A1["采集跑在 agent 循环的热路径上<br/>每追加一条事件同步走一趟"] --> A2["而攒批和重试天生是要等的"]
        A2 --> A3["那个「要等的」<br/>迟早会拖住那个「不能等的」"]
    end
```

```mermaid
flowchart TD
    F["每个「回合 + 步骤」只交出第一条流式分块"] --> F1["当作「这个步骤开始出字了」这一个信号"]
    F1 --> F2["内容不会丢<br/>那个步骤装配好的完整消息里是逐字节完整的"]
    F2 --> F3["于是介质上序号有洞是常态<br/>永远不是丢数据的信号"]
```

```mermaid
flowchart TD
    N5["其余三条"] --> N51["交接游标标的是「交出去」，不是「送到」<br/>再往后的投递是宿主的事，采集侧看不见"]
    N5 --> N52["没有游标时退回「第一条活事件减一」，不是 0"]
    N5 --> N53["运维记录只为已认领的会话产生<br/>所以「按需采集不产生运维记录」自动成立"]
    N52 -.->|"构造种子里的内容早就以另一个身份离开过进程：<br/>同一个身份在上一个进程里恢复、或者父会话的流<br/>重新交一遍等于重复上报"| N52
```

规则和接收器都是**部署方挂上来的**代码，所以本包兜住它们的崩溃：它们炸了不该把 agent 循环一起炸掉——上报是尽力而为的观察，不是业务。

## 生命周期与并发

### 装配顺序

这棵树里没有服务注册这一层，依赖全部由装配方显式递进来。

```mermaid
flowchart TB
    A1["① 打开介质，构造那道缝的实现<br/>装上编排层，挂到会话存储的四条观察者上"] --> A2["② 建折叠注册表<br/>把各个域的单元登记进去"]
    A2 --> A3["③ 打开缓存用的存储域<br/>构造折叠进度缓存，两个阈值必填"]
    A3 --> A4["④ 装耐久屏障<br/>一次挂齐三条，拿住返回的注销函数"]
    A4 --> A5["⑤ 要上报就构造采集侧<br/>在相应位置调那七个方法"]
    A5 -.->|"拆卸按反序"| A4
    A4 -.-> A3
    A3 -.-> A2
    A2 -.-> A1
```

顺序不是随便排的——每一步都依赖上一步的产物：缓存要注册表和服务面，屏障要服务面已经装好。拆卸必须反序，理由同样是依赖：先拆下面的会让上面的对着一个已经没了的东西调。

几处所有权约定：折叠进度缓存不关它用的那个存储域（谁打开谁关）；屏障的注销函数按反序摘；编排层关闭时排干未落地的批。

第一步里还有一个次序是承重的：

```mermaid
flowchart LR
    subgraph BAD13["先登记那四条观察者、后登记排干"]
        A1["拆的时候先跑排干"] --> A2["一边排一边有新的写进来"]
        A2 --> A3["永远等不到静止"]
    end
```

```mermaid
flowchart LR
    subgraph GOOD13["先登记排干、后登记那四条观察者"]
        B1["作用域按登记的反序拆"] --> B2["拆的时候先摘观察者、再跑排干"]
        B2 --> B3["事件的入口<br/>在最后一趟排干开始之前就关死了"]
    end
```

另外，装载之前就已经存在的活会话不会再补发一次「创建」，所以装载的末尾会把它们一次性入册；热替换之后重新装载走的就是这条路。

## 失败语义

全树只有两种失败姿势，判据只有一条：

```mermaid
flowchart TB
    Q["某件事失败了"] --> A{"它失败会不会造成一段<br/>「真的发生过、但没人记得」的历史"}
    A -->|"会"| FC["关门<br/>整条路断掉，后面一步都不许走"]
    A -->|"不会"| B{"它失败会不会让人<br/>读到一个错的值"}
    B -->|"会"| FC
    B -->|"不会，只是下次慢一点"| FS["尽力而为<br/>记一条告警，接着走"]
```

判断一个新写的失败路径该走哪边，就问这两个问题。

### 三道判据的次序不能换

```mermaid
flowchart LR
    D1["① 身份对不对"] --> D2["② 格式版本对不对"] --> D3["③ 词汇里有没有不认识又必需的类型"]
    D1 -.->|"身份不对就说明拿错了东西<br/>那时候版本号是谁的都不重要"| D2
    D2 -.->|"版本不对说明后面的结构<br/>本构建根本没法按今天的形状去解<br/>那时候「有个没见过的类型」是一句会误导人的话"| D3
```

### 关门的

| 场景 | 行为 |
|---|---|
| 读回来的头上写的会话身份不是请求的那个 | 拒。这道判据必须排在**发布任何状态之前**：介质要是把甲的存档当成乙的交出来，乙就会顶着甲的历史活过来 |
| 日志格式版本不匹配 | 直接拒收，不迁移。而且这**不是损坏**——原始日志还在原地躺着，给使用者的提示是「升级运行时」，绝不能说「数据损坏」 |
| 日志里有本构建不认识、又没标可跳过的事件 | 拒的是**整份日志**，不是那一条事件 |
| 读回来的存档自己不成立 | 裹成一条损坏。但格式拒绝不许再裹一层损坏，那会把「换个版本就能读」误报成「没救了」 |
| 耐久屏障刷不下去 | 模型请求不发、工具不跑、步骤不进 |
| 认领活会话时构造种子盖不住已落地的前缀 | 拒。说明这个活会话和那份存档不是一回事 |
| 脱敏规则返回错误 | 那条记录被扣下，不交给接收器 |
| 上报记录验不过 | 扣下并记一条日志。接收器多半要把它排成一种线格式，在那儿炸没人查得出来 |

### 尽力而为的

| 场景 | 行为 |
|---|---|
| 折叠进度写失败 | 只记一条告警，缓存留在旧位置。下次冷读多折一段尾巴 |
| 缓存行版本对不上 / 绑到另一段日志 | 丢掉那一行，退回重折 |
| 缓存行解不开 | 退回重折，**但必须留下一条告警** |
| 事件负载在折叠里读不回来 | 当作一条不相干的事件放过 |
| 脱敏规则或接收器崩了 | 兜住，不让 agent 循环跟着炸 |

「缓存行解不开」为什么必须留告警：

```mermaid
flowchart LR
    A["版本对得上却解不开"] --> B["说明这个构建自己写坏了那一行"]
    B --> C["而它的症状只是「每次冷读都慢一点」"]
    C --> D["没有任何人会去查"]
```

### 崩溃修复

一次崩溃会在日志上留下两种痕迹，处理方式完全不同：

```mermaid
flowchart TB
    C["读回来一份存档"] --> A{"介质挂了断尾凭据吗"}
    A -->|"挂了"| T["后面还有一截写坏的尾巴<br/>凭据由介质自己定义，编排层不看"]
    A -->|"没挂"| B["前缀本身是干净的"]
    T --> R["原样递回给那个介质<br/>由它去截"]
    B --> D{"最后一个回合收尾了吗"}
    R --> D
    D -->|"收了"| OK["这份日志本来就是平的"]
    D -->|"没收"| E["从事件流本身算出该补哪几条收尾事件"]
    E --> F["把它们接在后面<br/>补出来的字节是确定的，跑两遍一样"]
    F --> G["所以崩溃修复可以安全重跑"]
```

两件事拆得很干净：「写坏的尾巴」是介质的事，编排层只知道凭据非空意味着后面挂着一截要截掉的东西；「没收尾的回合」是词汇层的事，它算出来的那几条是确定的。

事务型的那个自带介质不存在第一种痕迹：

```mermaid
flowchart LR
    A["一次写就是一个事务"] --> B["要么整批提交，要么一条都没有"]
    B --> C["它的断尾凭据恒为空"]
    C --> D["一旦收到非空的凭据"]
    D --> E["说明编排层把别的介质的凭据递错了地方<br/>当场拒绝，不去猜它是什么意思"]
```
