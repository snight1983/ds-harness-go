# 会话日志与派生状态（`sessionlog/`）

本文讲会话日志这一条线：事件词汇，加上围着它转的九个包。这九个包分住在 `sessionlog/projection`、`feature/` 和 `adapter/` 三处，所以本文按职责编排，不按目录编排。活会话对象和会话检索不在本文范围内，只在需要说明接缝时点到名字。

下文的运行链路需要宿主显式接线：创建投影注册表、登记投影定义，并在会话事件提交后调用投影驱动和缓存观察入口。仅注册投影函数或创建缓存对象，不会自动订阅所有会话。`sessionlog/snapshot` 是测试日志快照工具，不参与正常的日志读写和会话恢复。

```mermaid
flowchart LR
    P["产品 / 设计"] --> P1["定位整节<br/>架构里的全景与三级读法<br/>失败语义的判定图"]

    D3["研发：只是用它"] --> D4["架构<br/>装配顺序<br/>失败语义"]
```

## 定位

### 为什么需要这棵树

一次会话里发生过的事，如果只活在内存里，那么进程一没，它就等于没发生过。

```mermaid
flowchart LR
    subgraph BAD["只把会话记在内存里"]
        A1["模型请求发出去<br/>钱开始花"] --> A2["工具跑起来<br/>文件被写了"]
        A2 --> A3["崩溃"]
        A3 --> A4["重新打开<br/>这两件事一件都不在"]
        A4 -.->|"世界上真的发生过<br/>但没人记得"| A1
    end
```

```mermaid
flowchart LR
    subgraph GOOD["受屏障保护的派发动作之前，先把已有日志刷到耐久介质"]
        B1["要发模型请求<br/>要跑工具"] --> B2["先把已经记下的那一段<br/>刷到耐久为止"]
        B2 --> B3{"刷得下去吗"}
        B3 -->|"刷得下去"| B4["放行<br/>动作跑出去"]
        B3 -->|"刷不下去"| B5["整条路断掉<br/>宁可这次做不成"]
    end
```

这棵树回答的就是这一件事：**一次会话里发生过什么，怎么记下来、怎么存住、怎么读成能用的东西。**

### 产品在界面上看到的四件事

```mermaid
flowchart LR
    U1["收到可用于起名的用户消息后生成兜底名<br/>可选模型更新；手动改名后钉住"] --> T1["标题那两个包"]
    U2["会话详情里的几个数字<br/>怎么翻页怎么压缩都不变"] --> T2["会话数字"]
    U3["会话列表读取缓存记录<br/>不用把历史读一遍"] --> T3["折叠进度缓存"]
    U4["模型或工具执行前<br/>先保存已经提交的日志"] --> T4["耐久屏障"]
```

第四条是这棵树存在的根本理由。模型请求一发出去钱就开始花、回答也开始在世界上存在；工具一跑起来文件就被写了、请求就被发了。这些事撤不回来。

屏障保证的是执行前已有日志的耐久性，不保证完整记录所有已发生的费用或工具结果。请求发出后、用量返回前，或者结果追加后尚未落盘时崩溃，仍可能缺少结果和用量记录；外部副作用是否已经发生，也不能仅凭缺少结果事件判断。

### 一条贯穿全树的原则

```mermaid
flowchart TD
    L["日志是事件记录的依据"] --> A["投影按日志计算<br/>可用检查点用于续算"]
    A --> B["重建所需事件仍完整保留时<br/>缓存丢失只增加重算成本"]
    A --> C["旧事件已裁剪且没有可用检查点时<br/>只能重算现存日志，状态可能缺失"]
    B --> D["后台缓存写失败记告警<br/>保留旧缓存供下次恢复"]
    L --> E["耐久屏障失败<br/>不放行下一次请求或工具执行"]
```

本仓库明确允许裁剪日志头部，也接受重算后丢失被裁剪事件对应的状态，见[会话日志上限](../session-log-limit.md)。因此，不能把“缓存随时可丢”理解成“业务数据永远可恢复”；若用投影承载必须长期保留的商品卡片等数据，需另行保证其完整恢复所需的事件或状态仍被保留。


### 三级读法

同一份状态有三条读路径，代价递增：

```mermaid
flowchart LR
    A["走活会话<br/>内存，零读写"] --> A1["实时界面<br/>当前请求"]
    B["只看已经存下的进度<br/>读取一条缓存记录，值可能旧"] --> B1["列表页"]
    C["存下的进度 + 日志尾巴<br/>读一截，折完写回"] --> C1["点开一个冷会话"]
    D["整读<br/>从存档现存的最前面"] --> D1["缓存作废时的兜底"]
    A -.->|"越往右越贵"| B
    B -.-> C
    C -.-> D
```

列表页可以走第二级，详情页需要较新状态时可以走第三级。实际延迟取决于存储和日志尾巴长度，缓存机制不保证固定的响应时间。

阶梯往下退是设计内的：

```mermaid
stateDiagram-v2
    state "第二级：只看存下的进度" as L2
    state "第三级：进度 + 日志尾巴" as L3
    state "整读：从现存最前面重折" as L4
    L2 --> L3 : 要实时的值
    L2 --> L4 : 缓存缺失 / 版本变化
    L3 --> L4 : 绑到了另一段日志 / 日志被崩溃修复截过尾
    L4 --> L2 : 折完写回，下次起点更近
```

```mermaid
flowchart LR
    A["读侧需要区分的情况"] --> B["仅查看缓存<br/>值可能旧，缺失或解不开的键不返回"]
    A --> C["从现存日志重建<br/>被裁剪事件对应的状态可能缺失"]
    A --> D["存储读取或重建失败<br/>返回错误"]
```

箭头是本图所列单元之间的依赖，不是完整的 Go 导入关系。词汇层不依赖活会话服务，但会使用 `llm` 的消息类型。自带介质是接缝的使用者，装配方自己的介质站在同一个位置。右侧使用者可按需装配：统计和标题使用投影机制，标题模型实现依赖标题接口，遥测直接消费会话事件。

一张表看完十个单元的能力和它最要紧的那条边界：

| 单元 | 能力一句话 | 最要紧的一条边界 |
|---|---|---|
| 词汇层 | 事件长什么样、日志立不立得住 | 不持有任何活对象 |
| 落地接缝 + 编排 | 那道缝 + 按会话串行的编排 | 不是具体介质 |
| 自带的那个介质 | 一个会话一条流，接到日志集上 | 没有逐字节原始存档，也不认路 |
| 耐久屏障 | 三处副作用边界上的屏障 | 只喊「现在刷」，不判断「有没有东西要刷」 |
| 折叠机制 | 事件折成当前状态 | 只提供机制，不提供内容 |
| 折叠进度 | 进度落地 + 两级带介质读 | 是恢复缓存；丢弃后只能依赖现存日志重建 |
| 会话数字 | 从整份日志折出那几个数 | 数步骤收尾事件，不数装配好的助手消息 |
| 会话标题 | 标题状态与三种来路 | 服务查询从日志折叠；注册的标题投影另有内存状态 |
| 拿模型起标题 | 一次辅助模型调用的全部策略 | 只收一个窄接口，不收整个模型运行时 |
| 外发上报 | 上报的采集侧 | 交出去之后的那一段一个字都不建模 |

### 词汇层

它定义一条会话记录的结构，并提供校验、折叠和修复的纯函数；不负责订阅会话事件或操作存储。

```mermaid
flowchart TB
    V["词汇层做四件事"] --> V1["定义一条日志条目：<br/>序号 · 时间 · 类型 · 负载<br/>十三种具名负载 · 会话头 · 会话身份"]
    V --> V2["判一份日志立不立得住：<br/>序号 · 回合与步骤配对 · 工具调用配对<br/>读到不认识的类型怎么办"]
    V --> V3["把一份崩在半路的日志<br/>补齐成模型提供方肯收的历史"]
    V --> V4["把日志折成模型可见历史"]
```

事件负载**故意不解成联合类型**：

```mermaid
flowchart LR
    subgraph BAD4["解成一个封闭联合"]
        A1["核心词汇表登记 13 种类型<br/>其他包可以扩展自己的事件类型"] --> A2["核心解码器读到其他类型"]
        A2 --> A3["解成「未知」"]
        A3 --> A4["排回去时把它的字段丢掉"]
        A4 -.->|"而日志是持久的<br/>丢掉的是别人写下的历史"| A2
    end
```

```mermaid
flowchart LR
    subgraph GOOD4["负载就是一段原始字节"]
        B1["读到不认识的类型"] --> B2["原样保管那段字节"]
        B2 --> B3["需要具名字段时才按需解一次"]
    end
```

不认识的负载可以原样保管；是否允许恢复这份日志，由词汇检查另行判断。已知类型的负载格式损坏，则可能在解码或日志校验时返回错误。

```mermaid
flowchart TD
    E["读到一条事件"] --> Q{"本构建认识这个类型吗"}
    Q -->|"认识"| OK["按具名字段用"]
    Q -->|"不认识"| Q2{"这条标了可跳过吗"}
    Q2 -->|"标了"| SKIP["放过，原样保管字节"]
    Q2 -->|"没标"| REJ["拒的是整份日志"]
    REJ -.->|"一条不认识的必需事件<br/>可能改变后面整段日志的解释方式<br/>静默跳过等于重建出一个错的会话"| REJ
```

它还有一条边界：**不解释业务含义**。它知道一条「要调这个工具」后面该配一条「工具给了什么」，不知道那个工具干了什么。拆出来单放一个包的理由是落地那一层只需要值和纯函数，混在一起它就得连着一整套用不到的东西一起立起来。

### 落地接缝与编排

```mermaid
flowchart TB
    L3["第三层：编排<br/>按会话身份串行化每次操作<br/>挂在会话存储的四条观察者上<br/>认领活会话 · 维护准备池 · 编排崩溃修复 · 关闭时排干"] --> L2["第二层：攒批控制器<br/>不认识会话，只认识<br/>「攒一批、到点写下去、写失败了把缓冲留着」"]
    L2 --> L1["第一层：词汇与纯函数<br/>介质的最小原始能力集 · 使用方的服务面<br/>跨介质的那几种值 · 三道判据 · 把中断的日志补平 · 认领时那道判据"]
```

介质的五项可选本事由类型探测发现，有就用、没有就当场说清楚：按序号直接寻址、可关闭、可从最老一头弹掉、能整份删掉、能指出一份逐字节的原始存档。前三项和第五项缺席时退回慢做法或降级；**删除缺席时是一句明确的拒绝**——回报一句「删成功了」而其实什么都没删，会让使用方的列表刷新之后那一条又冒出来。

「整份删掉」和「从最老一头弹掉」不是一回事：

```mermaid
flowchart TD
```

### 耐久屏障

它自己一行状态都不存，装上去之后只做一件事：在「这一步的后果将要跑到会话日志管不着的地方去」之前，先把日志已经记下的那一段刷到耐久为止。

```mermaid
flowchart LR
    subgraph inside["会话日志管得着的世界"]
        S1["追加事件<br/>随时可以重来"]
    end
    B1{{"屏障 ①<br/>模型请求派发前"}}
    B2{{"屏障 ②<br/>顶层工具调用派发前"}}
    B3{{"屏障 ③<br/>每个步骤开始前"}}
    subgraph outside["管不着的世界：撤不回来"]
        O1["模型开始出字<br/>钱开始花"]
        O2["写文件 · 发请求 · 跑命令"]
        O3["下一次请求"]
    end
    S1 --> B1 --> O1
    S1 --> B2 --> O2
    S1 --> B3 --> O3
```

| 边界 | 刷的是什么 | 为什么是这里 |
|---|---|---|
| 模型请求派发前 | 这次请求 | 一发出去钱就开始花，模型也开始产出。此后崩溃，恢复出来的会话缺掉这次请求，而它的回答已经在世界上存在过了 |
| 顶层工具调用派发前 | 「我要调这个工具」那条记录及此前已提交事件 | 工具体可能执行写文件、发请求等外部副作用 |
| 每个步骤开始前 | **上一步**提交的那一批 | 放在下一步开头而非上一步结尾——一个步骤结尾未必有下文，而下一次请求一定有 |

装卸是一对：

```mermaid
flowchart LR
    A["一次挂齐三条"] --> B["返回一个把它们一起摘下来的函数"]
    A --> C{"中途装不上"}
    C --> D["按反序摘干净再报错"]
    D -.->|"半装上去比装不上更坏"| D
```

它做的唯一判断是「这次该不该我管」：

```mermaid
flowchart TD
    Q["一次钩子触发"] --> Q1{"认得出是哪个会话吗"}
    Q1 -->|"认不出"| P1["放过<br/>模型调用未带会话 ID 或找不到活会话<br/>工具调用缺少发起 Agent 上下文"]
    Q1 -->|"认得出"| Q2{"是有父调用的嵌套工具调用吗"}
    Q2 -->|"是"| P2["工具派发屏障放过<br/>该策略只保护顶层工具调用"]
    Q2 -->|"否"| GO["刷"]
```

是否属于“辅助调用”不是模型屏障的判断条件。标题模型实现会传入会话 ID；只要经过装有该规则的模型运行时，且能找到活会话，也会先刷日志。嵌套调用的跳过规则只适用于工具派发屏障。

```mermaid

    N["它不做什么"] --> N1["只喊「现在刷」<br/>不判断「有没有东西要刷」"]
    N --> N2["不拥有存储介质"]
    N --> N3["不负责状态缓存的数量和时间节流"]
    N --> N4["三条规则本身写死<br/>装配方只能选装不装、给谁装"]
    N --> N5["模型看不见它<br/>它不在工具表里，模型无从调用<br/>也不参与「要不要刷」的决定"]
```

### 折叠机制

日志是流水账，界面要的是余额。这就是那台从流水账算余额的机器——而且是增量算的，来一条加一条。

```mermaid
flowchart LR
    E1["事件 n"] --> A1["折一次"]
    S0["状态停在 n-1"] --> A1
    A1 --> S1["状态推到 n"]
    A1 --> C{"变了吗"}
    C -->|"变了"| N["把新值通知出去"]
    C -->|"没变"| X["什么都不发"]
    C -.->|"「变没变」是显式返回的<br/>Go 没法像 JS 那样靠引用相等判断"| C
```

开发者注册一份投影定义，提供键、初始状态、状态更新函数、状态版本、解码函数，以及可选的对外视图。宿主在事件提交后调用 `Registry.Drive`；注册表负责逐会话更新状态、记录已处理序号并发出变更通知。注册表本身不订阅会话，也不操作数据库。

同一份注册表中的投影规则适用于送入它的所有会话，投影状态按会话 ID 隔离。它不是进程级的全局注册表，也不会自动对所有 Agent 生效。

```mermaid
flowchart LR
    K1["折叠键"] --> K2["会话身份"] --> K3["单元格：状态 + 折到第几条"]
    K3 -.->|"内存里就是这两跳定位"| K1
```

对外四件事：登记（引用计数、注销幂等）、推进、读（三级）、出检查点。

**事件可以携带完整状态，也可以携带增量。**

```mermaid
flowchart TD
    subgraph DELTA["增量事件：例如步骤结束"]
        A1["当前步骤数"] --> A2["收到一条步骤结束事件，加一"]
        A2 --> A3["依赖已有状态<br/>恢复时需要可用检查点或足够的历史"]
    end
```

```mermaid
flowchart TD
    subgraph FULL["完整状态事件：例如待办清单"]
        B1["事件携带更新后的完整清单"] --> B2["用这一份替换当前清单"]
    end
```

投影机制不强制事件必须携带整值。内置会话统计就是累加事件得到的状态；如何更新由各自的 `Apply` 决定。完整状态事件也需要保留到可恢复的日志范围内，才能在缓存丢失后重建。

检查点交出去的是**排出去的字节**，不是活引用：

```mermaid
flowchart LR
    subgraph BAD6["交出活引用"]
        C1["水位缓存是这张表权威的可变状态"] --> C2["一个拿到活引用的调用方"]
        C2 --> C3["能顺着它把后面每一次读切都改坏"]
    end
```

```mermaid
flowchart TD
    N2["它不做什么"] --> N21["它是固定代码的确定计算<br/>不是让模型分析聊天内容<br/>同一份合法日志加同一版规则<br/>必须得到同样的结果"]
    N2 --> N22["只提供机制，不提供内容<br/>本包不认识任何一个折叠单元的语义"]

    N2 --> N24["状态必须能原样进出 JSON<br/>这是检查点能落地的前提"]
    N2 --> N25["一份检查点行永远不是权威：<br/>版本对不上、或它声称的水位超过日志末尾<br/>就丢掉重折"]
```

### 折叠进度存住

投影注册表在正常运行时增量更新内存状态，读取已经建立的状态不会从头重算。这个缓存模块把状态和已处理序号保存下来，让没有活会话时的读取、进程重启后的冷读可以少重放日志。仅注册投影函数不会产生持久检查点，还需要接上此缓存模块。

```mermaid
flowchart LR
    R["每个会话一条记录"] --> R1["上一次被折到哪个序号"]
    R --> R2["折到那里时每个单元的状态"]
    R1 --> U1["最快的持久缓存读法：<br/>从存储读取一条记录，不读取日志"]
    R2 --> U1
    R1 --> U2["冷读那一级：<br/>记录 + 从恢复地板起的一截尾巴<br/>折完写回去，下一次起点更近"]
```

四个写触发点：

```mermaid
flowchart TD
    W["什么时候写"] --> W1["回合结束<br/>不节流，必写，异步"]
    W --> W2["攒够 N 条事件<br/>节流，阈值可配，异步"]
    W --> W3["间隔到点<br/>节流，阈值可配，异步"]
    W --> W4["会话脱离<br/>不节流，必写，同步，错误交回调用方"]
```

这些触发依赖宿主在事件提交后调用 `Cache.Observe`、在会话卸载时调用 `Cache.Detach`。间隔计时从出现待保存的新事件时启动，不是空闲期间一直写。另有两条显式路径：宿主可以直接调用 `Cache.Write`；`ColdSnapshot` 重建完成后也会尝试写回检查点。

两个阈值**必填、没有缺省值**：

```mermaid

    subgraph BAD7["给一个默认值"]
        A1["写太密"] --> A2["每条事件一次强制落地"]
        B1["写太疏"] --> B2["崩溃之后重放很长一段"]
        A2 -.->|"代价只有部署方衡量得了<br/>猜一个默认值等于替装配方<br/>做了一个它自己都不知道做过的决定"| B2
```

### 会话标题

```mermaid
stateDiagram-v2
    state "没有名字" as S0
    state "兜底名：截第一条人类消息的前几个词" as S1
    state "模型起的名" as S2
    state "用户自己改的名：钉住" as S3
    S0 --> S1 : 用户发第一条消息，同步、确定、不花钱、立刻落地
    S1 --> S2 : 模型那一步异步跑完，顶掉兜底
    S1 --> S3 : 用户手动改名
    S2 --> S3 : 用户手动改名
    S3 --> S3 : 后续消息不再排期，在途的自动生成当场作废
    S3 --> S2 : 显式刷新且模型成功生成
    S3 --> S1 : 显式刷新且未登记模型生成器
```

接好标题服务后，有可用于起名的用户消息且追加成功时，会同步生成确定性的兜底名。空会话、尚无可用消息或写入失败时，仍可能没有标题。可选的模型生成成功后更新标题，用户手动改名后则停止自动覆盖，直到显式刷新。

标题为什么必须是日志上的一条事件，而不是会话头上一个可以随手改的字符串：

```mermaid

    subgraph BAD10["存成会话头上一个可变字段"]
```


## 生命周期与并发

### 装配顺序

这棵树里没有服务注册这一层，依赖全部由装配方显式递进来。

```mermaid
flowchart TB
    A1["① 打开介质，构造那道缝的实现<br/>装上编排层，挂到会话存储的四条观察者上"] --> A2["② 建折叠注册表<br/>把各个域的单元登记进去"]
    A2 --> A3["③ 打开缓存用的存储域<br/>构造缓存，提供 Flush 和两个阈值"]
    A3 --> Wire["接好会话通知：<br/>提交后先 Drive，再 Observe<br/>卸载时 Detach"]
    Wire --> A4["④ 装耐久屏障<br/>一次挂齐三条，拿住返回的注销函数"]
    A4 --> A5["⑤ 要上报就构造采集侧<br/>在相应位置调那七个方法"]
    A5 -.->|"拆卸按反序"| A4
    A4 -.-> Wire
    Wire -.-> A3
    A3 -.-> A2
    A2 -.-> A1
```

这是满足依赖的一种装配顺序，不是每个模块都依赖紧邻的前一个：缓存依赖注册表、存储和刷盘入口，屏障依赖会话、模型和工具运行时。关键是先准备依赖，再连接通知；卸载时先停止新工作，在存储关闭前完成会话卸载和必要的刷盘。

`Registry.Drive`、`Cache.Observe`、`Cache.Detach` 都是显式入口。`Session.Append` 会通知会话观察者，但不会自动发现某个投影注册表或缓存实例。宿主必须接好这些调用。缓存的 `Flush` 也必须连接到真正的日志落盘屏障，不能只把日志排进后台队列就返回成功。

几处所有权约定：折叠进度缓存不关它用的那个存储域（谁打开谁关）；屏障的注销函数按反序摘；编排层关闭时排干未落地的批。

第一步里还有一个次序是承重的：

```mermaid
flowchart LR
    subgraph BAD13["先登记那四条观察者、后登记排干"]
        A1["拆的时候先跑排干"] --> A2["一边排一边有新的写进来"]
        A2 --> A3["永远等不到静止"]
    end
```

```mermaid
flowchart LR
    subgraph GOOD13["先登记排干、后登记那四条观察者"]
        B1["作用域按登记的反序拆"] --> B2["拆的时候先摘观察者、再跑排干"]
        B2 --> B3["事件的入口<br/>在最后一趟排干开始之前就关死了"]
    end
```

另外，装载之前就已经存在的活会话不会再补发一次「创建」，所以装载的末尾会把它们一次性入册；热替换之后重新装载走的就是这条路。

```mermaid
flowchart TB
    S["读一个已落地会话的状态"] --> R["读缓存行"]

    F --> T["从地板读一截日志尾巴<br/>带回存档头和存档起点"]
    T --> I{"缓存行绑的身份<br/>和存档头对得上吗"}
    I -->|"对不上"| W["整读：从存档现存的最前面重折"]
    I -->|"对得上"| U{"每一行都可用吗<br/>版本对得上 · 序号至少为尾巴起点减一<br/>不超过尾巴末尾"}

    U -->|"有不可用的，而这截不是现存的全部"| W
    U -->|"有不可用的，但这截已经是全部"| Z["丢掉那些行，从初值重折"]
    G --> P["把刷新过的检查点写回<br/>尽力而为，失败只记一条告警"]
    Z --> P
    W --> P
```

缓存身份不符、检查点不可用或解码失败时，冷读会尝试从现存日志重建。缓存读取、日志读取以及重建过程本身仍可能返回错误。若所需旧事件已被裁剪，重建结果可能缺少此前的状态；写回失败则记告警，不改变本次已经得到的读结果。

两处容易忽略的细节：

```mermaid

    subgraph BAD14["从已处理序号的下一条开始读"]
        A1["读回来的尾巴证明不了<br/>存储里的日志还延伸到哪儿"] --> A2["一份被崩溃修复截短了的日志发现不了"]
        A2 --> A3["一行过期的数据被当成当前值端出去"]
    end
```

```mermaid
flowchart LR
    subgraph GOOD14["从下一条往回让一条，包含已处理的那条"]
        B1["读回来的尾巴<br/>就能证明日志还延伸到哪儿"] --> B2["被截短的日志会被当场发现"]
    end
    subgraph POINT["「整读」的起点也是个变量，不是 0"]
        C1["日志会从最老的一头弹出事件"] --> C2["整读问的是<br/>「存档现存最早那条是第几号」<br/>由介质那一侧说出来"]
```

例如所有已注册投影中最小的已处理序号为 100，就从序号 100 开始读取，用它检查日志末尾；各投影只计算大于自己已处理序号的事件，不会重复计算已经处理的部分。若日志头部已裁剪到 100 之后，读取从现存起点开始，再按该起点判断检查点是否可用。

## 失败语义

运行控制和后台观察采用不同的失败处理；读取与显式保存接口还会把错误交给调用方。

```mermaid
flowchart TB
    Q["某件事失败了"] --> A{"它失败会不会造成一段<br/>「真的发生过、但没人记得」的历史"}
    A -->|"会"| FC["关门<br/>整条路断掉，后面一步都不许走"]
    A -->|"不会"| B{"它失败会不会让人<br/>读到一个错的值"}
    B -->|"会"| FC
    B -->|"不会，只是下次慢一点"| FS["尽力而为<br/>记一条告警，接着走"]
```

这是设计上的取舍方向，不表示所有存储故障都会立即停止整个 Agent。屏障失败会阻止对应动作；追加后的观察者错误由会话记录；缓存后台写失败记告警；显式读取、写入和卸载的错误由调用方处理。

### 三道判据的次序不能换

```mermaid
flowchart LR
    D1["① 身份对不对"] --> D2["② 格式版本对不对"] --> D3["③ 词汇里有没有不认识又必需的类型"]
    D1 -.->|"身份不对就说明拿错了东西<br/>那时候版本号是谁的都不重要"| D2
    D2 -.->|"版本不对说明后面的结构<br/>本构建根本没法按今天的形状去解<br/>那时候「有个没见过的类型」是一句会误导人的话"| D3
```

### 关门的

| 场景 | 行为 |
|---|---|
| 读回来的头上写的会话身份不是请求的那个 | 拒。这道判据必须排在**发布任何状态之前**：介质要是把甲的存档当成乙的交出来，乙就会顶着甲的历史活过来 |
| 日志格式版本不匹配 | 直接拒收，不迁移。而且这**不是损坏**——原始日志还在原地躺着，给使用者的提示是「升级运行时」，绝不能说「数据损坏」 |
| 日志里有本构建不认识、又没标可跳过的事件 | 拒的是**整份日志**，不是那一条事件 |
| 读回来的存档自己不成立 | 裹成一条损坏。但格式拒绝不许再裹一层损坏，那会把「换个版本就能读」误报成「没救了」 |
| 耐久屏障刷不下去 | 模型请求不发、工具不跑、步骤不进 |
| 认领活会话时构造种子盖不住已落地的前缀 | 拒。说明这个活会话和那份存档不是一回事 |
| 脱敏规则返回错误 | 那条记录被扣下，不交给接收器 |
| 上报记录验不过 | 扣下并记一条日志。接收器多半要把它排成一种线格式，在那儿炸没人查得出来 |

### 尽力而为的

| 场景 | 行为 |
|---|---|
| 后台检查点写入或冷读写回失败 | 记告警，后续再尝试恢复；恢复能力受日志保留范围限制。显式 `Write` 和 `Detach` 的错误仍返回调用方 |
| 缓存行版本对不上 / 绑到另一段日志 | 冷读舍弃不适用的检查点后重建；身份不符时整份缓存都不用。只查看缓存时不返回对应值 |
| 缓存行解不开 | 冷读记告警并退回重折；只查看缓存的读法会省略解不开的键 |
| 内置统计、标题投影读不回事件负载 | 保留原状态；其他投影按各自实现处理，不由注册表统一忽略 |
| 脱敏规则或接收器崩了 | 兜住，不让 agent 循环跟着炸 |

冷读发现「缓存行解不开」时为什么要留告警：

```mermaid
flowchart LR
    A["版本对得上却解不开"] --> B["可能是写入缺陷、数据损坏<br/>或状态结构变化却没升级版本"]
    B --> C["而它的症状只是「每次冷读都慢一点」"]
    C --> D["没有任何人会去查"]
```

### 崩溃修复

一次崩溃会在日志上留下两种痕迹，处理方式完全不同：

```mermaid
flowchart TB
    C["读回来一份存档"] --> A{"介质挂了断尾凭据吗"}
    A -->|"挂了"| T["后面还有一截写坏的尾巴<br/>凭据由介质自己定义，编排层不看"]
    A -->|"没挂"| B["前缀本身是干净的"]
    T --> R["原样递回给那个介质<br/>由它去截"]
    B --> D{"最后一个回合收尾了吗"}
    R --> D
    D -->|"收了"| OK["这份日志本来就是平的"]
    D -->|"没收"| E["从事件流本身算出该补哪几条收尾事件"]
    E --> F["把它们接在后面<br/>补出来的字节是确定的，跑两遍一样"]
    F --> G["所以崩溃修复可以安全重跑"]
```

两件事拆得很干净：「写坏的尾巴」是介质的事，编排层只知道凭据非空意味着后面挂着一截要截掉的东西；「没收尾的回合」是词汇层的事，它算出来的那几条是确定的。

事务型的那个自带介质不存在第一种痕迹：

```mermaid
flowchart LR
    A["一次写就是一个事务"] --> B["要么整批提交，要么一条都没有"]
```

## 能力边界

```mermaid
flowchart TD
    Y["这棵树负责"] --> Y1["事件格式、负载、日志校验与崩溃修复"]
```
