# 凭据

## 定位

`credentials` 定义凭据引用、记录和提供方接缝，让模型配置只保存稳定引用，而不是把 API Key 或授权材料写进会话、设置或日志。

## 架构与数据模型

```text
配置中的 Ref
    |
    v
Provider.Resolve
    |
    +-- APIKeyRecord
    +-- GrantRecord
    |
    v
Resolved（仅在调用边界短暂使用）
```

`Ref` 是公开引用名；`Key` 由 scope 与 id 组成，用于后端记录寻址。`Record` 是封闭接口，当前支持 API Key 和 Grant 两种记录。`Info` 与 `RecordInfo` 只提供可展示元数据，不能泄露秘密值。

## 核心接口

`Provider` 负责解析引用、读取记录、列举元数据和原子更新；`Mutator` 根据当前记录决定是否写入。`Observer` 与 `Notifier` 把引用或记录变化通知给模型路由等消费者，监听器通过返回的取消函数解除。

`NewRef`、`NewKey` 和 `ParseKey` 执行严格语法校验，避免把路径、控制字符或含糊分隔符带入后端键空间。

## 配置界面看得到什么

值只有一个方向：写得进去，读不出来。

```text
        写                            读
 界面 ──值──> Provider.Set      界面 <──在不在 ──┐
                                    <──哪一层 ──┤ DescribeRefs
                                    <──能不能改─┘

                                值本身：没有这条线
```

「脱敏」在这里不是把值打码之后交出去，而是**根本没有交出值的那条路**。不给掩码是有意的：一个足够让人认出自己密钥的掩码，同样足够让别人往下猜；而界面要回答的「这一位配没配」本来就不需要看见值。

一屏凭据是一批行，`DescribeRefs` 一次把这一批问完，好让它们一起落定——拆成一个个问，先回来的行先渲染、后回来的行在旁边空着，而它们说的本该是同一个时刻的同一份配置。

这条路上另外两道关：

| 关 | 不过的话 |
|---|---|
| 每个名字都要是合法引用名 | 整次拒绝，不是跳过那一个（少一行和「没配置」在界面上长得一样） |
| 一次最多问 64 个 | 整次拒绝；挡的是一次已鉴权的请求让提供方开始一段没有上界的活 |

设置那一半的脱敏在 `settings` 包里：带 `RedactSecrets` 读出来的描述**把密钥字段整个摘掉**，而不是替换成掩码。两半是同一个原则。

## 人工授权流程

有一类凭据不是配出来的，是**跟人来回几趟换出来的**：打开一个页面、敲一个短码、等回调、拿到令牌。这几趟里，知道该怎么走的是插件，能跟人说上话的是界面，而两者互相不认识。`feature/authorization` 就是中间那一位。

```text
   插件                  authorization                 界面
（知道怎么走）            （中间人）              （能跟人说上话）

  登记一条流程  ────────>  ┌──────────┐
                          │ 谁认领哪条 │
                          │ 凭据      │
  跑起来  <───────────────│          │<──── 起一次授权，
    │                     │ 同一时刻   │      并把「怎么跟人说话」
    │  要问一句话 ───────> │ 只许一次   │ ───> 一起交进来
    │  <────────── 人的答话 │          │
    │                     │ 一次尝试   │
    └── 自己把凭据写下去 ──> │ 怎么算完   │ ───> 结果：成了 / 撤了 / 砸了
                          └──────────┘
```

值不经过这条缝。流程自己把凭据交给提供方写下去，这个包只核实两件事——这次尝试之内看见过一次写入，而且尝试结束之后那条记录还在。问出去的话和给出去的通知里永远不含密钥。

### 干到一半走人，第二天接着干

DSH 那份实现里，一次授权活在一个浏览器进程的闭包里，所以它只有两种状态：在跑，和不在。它自己的文档写着「flow 不可恢复」。

这个仓库的前提不一样——人可以关掉窗口第二天再来，一次授权可以起在这台机器上、接在那台机器上。所以一次尝试是数据库里的一条记录，于是多出第三种状态：

| 状态 | 意思 | 起一次新的会怎样 |
|---|---|---|
| 在跑 | 有一台机器攥着一份没过期的租约 | 拒绝：已经有人在跑了 |
| **停着** | 记录还在，跑它的那个进程没了 | **拒绝**，要人明说是接手还是撤掉 |
| 没有 | 这条凭据上一次尝试都没有 | 起一次新的 |

「停着」那一种既不是忙也不是闲。默认起一次新的会把上次攒下的进度悄悄扔掉，所以这个包不替人做这个决定。

### 接手不是恢复现场，是重跑一遍

一段正在跑的代码序列化不了，所以「接着上次干」不可能是把现场原样搬过去。做法是**重跑那条流程**，由流程自己读回上一次留下的脚印然后跳到那一步：

```text
第一次跑                          接手的那次跑

打开授权页            ┐            读回脚印 ──> 有 state 和 verifier
留下脚印 {state,…} ───┼─> 数据库 ─>  直接跳到「轮询令牌」
把人支去浏览器        │             （不再要一次授权码）
    ✗ 进程没了       ┘
```

留脚印这个动作顺带做三件事：续一次租、读回「有没有人要撤」、把进度写下去。一次来回办完，是因为这三件事本来就该在同一个时刻看同一份记录。

### 抢同一条凭据，只有一个能赢

记录键就是凭据键，所以「一个键上只有一次尝试」是数据库自己保证的，不靠任何一台机器的内存。攥着它的那台每隔租期三分之一续一次租；租约断了别的机器就能接手，而原来那台在下一次续租时发现记录已经易主，于是停手且**不结算**——那条记录不再是它的了。

撤销同理：撤的那一位和跑的那一位可能不在一台机器上，所以撤销是写进记录里的一个标记，攥着它的那台在下一次续租、发问或留脚印时读到它。

### 不做什么

- 不实现任何一条具体流程。OAuth、设备码、粘贴 API Key 都是登记方的事。
- 不渲染任何界面。怎么把话摆到人面前由调用方实现。
- 不碰凭据的值。
- 不自动重试，也不自动接手——一次停着的尝试要人明确选。

## 生命周期与并发

- Provider 的存储寿命由宿主管理，本包不创建数据库连接。
- Notifier 可以被并发调用；订阅和取消必须与通知安全共存。
- 监听器失败或 panic 不应阻断其他监听器，具体记录方式由宿主日志器承担。

## 失败语义

- 未找到、记录类型不匹配、引用损坏和后端失败必须区分；不得把后端错误伪装成“没有凭据”。

## 能力边界

- 记录序列化只用于受保护后端，不能写入普通应用日志。
- 展示接口必须使用脱敏信息，不能通过 `Info` 返回密钥正文。
- `credentials` 本身不实现加密、密钥轮换、OAuth 流程或访问控制；加密与轮换由 Provider 与宿主负责，人工授权那一段由 `feature/authorization` 承担（它同样不实现任何一条具体流程）。
- 凭据变更通知只表示需要刷新，不携带秘密值。
