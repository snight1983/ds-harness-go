# 大结果外置

## 定位

`spill` 定义把大段文本写到外部存储并返回稳定引用的接缝；`spill/policy` 把这项能力接到工具结果终结阶段，在超过阈值时外置内容，控制模型上下文占用。

## 架构

```text
工具原始文本
    |
    | 小于阈值 ----------------> 原样结果
    |
    | 大于阈值
    v
spill.Store.SaveText -> spill.Ref
    |
    v
模型看到摘要 + Locator
```

`SaveText` 带 Owner、Source 和正文，`Store` 返回 `Ref`。`Locator` 是后续读取位置的稳定描述，不应包含临时凭据。外置后的模型结果必须说明内容被移走以及如何恢复，不能只静默截断。

## 落地实现

`spill/textstore` 是这条接缝在本仓库的实现。它不认硬盘，只认 `fs` 那条文件系统接缝，所以换成对象存储是装配时的事，业务代码一行不动。

产物的落点长这样：

```text
<根>
 └── session-<会话 id 的哈希，12 位>       <- 按会话归拢，但句柄里不出现会话 id
      └── <16 位随机码>-<净化过的建议名>    <- 随机码负责不撞名，建议名只是给人看的尾巴
```

三件事值得单独说：

- **建议名永远不当路径用。** 它一路来自工具名，而工具名可以由插件自定。净化之后只剩字母、数字、点、下划线、连字符，所以它拼不出一段分隔符，也不可能变成「上一层」。
- **撞名报错，不覆盖。** 写入走「不存在才写」。真撞上了说明介质出了问题，而静默覆盖会毁掉在先那份产物——上层之所以敢把结果挪走，依据正是「挪走的那份还在」。
- **取回说明由装配方给。** 句柄是什么形状取决于装的是哪条文件系统，所以那段给模型看的「怎么把它读回来」是一项配置，不是写死的一句话。

不做启动清扫：保留期是介质自己的事（对象存储的生命周期规则、本地磁盘的定时任务），多副本部署下让每个副本各自去扫同一棵树既慢又没有协调。

## 策略

`policy.Config` 控制触发字节数、保留预览和来源标记。`Policy.Install` 注册工具结果 Finalize 钩子；它只处理文本结果，对结构化错误和已经外置的引用保持幂等。

外置发生在工具执行完成之后，因此程序化执行结果和审计信息仍可保留原始语义；模型可见表示根据预算缩小。

## 生命周期与并发

- Policy 不拥有 Store，卸载时只撤销工具管线钩子。
- 每次工具调用使用独立保存请求，可并发调用 Store。
- Context 取消必须传给 Store，取消后不得继续发布 Locator。

## 失败语义

- 保存失败时返回明确工具错误或按配置保留受限内容，不能声称已经生成可读取引用。
- 外置成功但引用无法序列化时整次终结失败，不能丢失原结果后返回空引用。

## 能力边界

- Spill 不是 Session 持久化，也不是通用文件上传。
- 这条接缝**只能写**，没有读的方法。取回靠宿主自己的通道，模型照着取回说明去调别的工具。
- 访问控制、保留期、加密和 Locator 解析由 Store 背后的那套介质负责。
- 外置减少模型上下文，不保证外部对象永久存在。
