# 用户交互

对应包：`feature/interaction/commands`、`feature/interaction/userquestions`、`feature/interaction/askuser`、`feature/interaction/userapproval`、`feature/interaction/permissionpresets`

## 定位

这五个包管的是同一件事的五个面：**人和这套装置之间怎么说话**。

模型和人说话只有一条正规通道——工具。但人和装置之间的对话远不止这一种：人可以主动敲一条命令，装置也可以停下来反问人一句，还可以在动手之前先请示一次。方向不同，能不能被模型看见也不同：

```mermaid
flowchart LR
    P(("人")) -->|"敲 /compact"| C["斜杠命令"]
    C -->|"结果只给人看"| P
    M(("模型")) -->|"调 ask_user 工具"| A["模型发问"]
    A -->|"答案变成工具结果<br/>回到模型手里"| M
    T["某个工具要动手"] -->|"先请示"| AP["审批"]
    AP -->|"放行 / 驳回"| T
    P -->|"挑一个档位"| PP["权限预设"]
    PP -->|"把审批策略拨过去"| AP
```

一句话分工：

| 谁发起 | 谁回答 | 模型看得见吗 |
|---|---|---|
| 人敲命令 | 装置 | **看不见**，斜杠命令不进上下文 |
| 模型发问 | 人 | 看得见，答案就是工具结果 |
| 工具要动手 | 人 | 看得见结局，看不见问答过程 |
| 人挑档位 | 装置 | 看得见档位换了，因为它会改系统提示里那句话 |

## 架构

五个包不是平级的。中间三个是**接缝**（只定形状，不画界面），外面两个是**用它的人**：

```mermaid
flowchart TD
    subgraph FACE["露给人和模型的一面"]
        CMD["斜杠命令注册表<br/>commands"]
        TOOL["ask_user 那件工具<br/>askuser"]
        PRE["权限档位<br/>permissionpresets"]
    end
    subgraph SEAM["接缝：定形状，不画界面"]
        UQ["向人发问<br/>userquestions"]
        UA["请示一次<br/>userapproval"]
    end
    TOOL --> UQ
    PRE -->|"把档位拨成策略"| UA
    UQ -.->|"插一个界面进来"| UI1(("终端 / 桌面 / 网页"))
    UA -.->|"插一个答复者进来"| UI2(("终端 / 桌面 / 网页"))
    CMD --> LOG[("会话日志")]
    UA --> LOG
    PRE --> LOG
```

这么切的理由：**一个无界面的装配**（批处理、回放、压测）只要不接那两个插头，模型就问不出问题、工具也请示不到人——不需要在每个包里再写一遍「现在没人，怎么办」。

## 斜杠命令：人对着装置本身说的话

### 为什么它不进模型

`/compact`、`/status` 这类命令是人对**这套装置**说的，不是对模型说的。让它们进上下文有两个坏处：白占预算，而且模型会以为自己可以决定这条命令跑不跑。

```mermaid
flowchart LR
    IN["/compact"] --> R["命令注册表"]
    R --> H["处理器"]
    H --> OUT["一段给人看的结果"]
    R -.->|"从不经过"| MODEL(("模型上下文"))
```

### 一次执行的七道关

```mermaid
flowchart TD
    A["一行 /名字 参数"] --> B["① 认形状<br/>只认斜杠后面紧跟行尾或一个空格<br/>参数原样往下传，不分词不展开"]
    B --> C["② 找定义<br/>先看这个 agent 自己的登记<br/>再看全局登记"]
    C --> D{"③ 围栏<br/>形状不对？名字不认得？已经取消了？"}
    D -->|"任一成立"| X["直接结束<br/>一个字节都不写"]
    D -->|"都不成立"| E["④ 落一条「开始跑」"]
    E --> F{"⑤ 带图片了吗"}
    F -->|"带了但这条命令没声明收图<br/>或者超了张数限额"| G["结算成错误结果<br/>被拒的图一张都不落盘"]
    F -->|"没带 / 收得下"| H["⑥ 跑处理器"]
    G --> I["⑦ 落一条「跑完了」"]
    H --> I
```

三处刻意的取舍：

- **第 ③ 关不写字。** 名字都不认得的一行输入，写进日志只会污染审计。
- **第 ④ 关写不进去就大声失败。** 因为第 ⑦ 关那条「跑完了」要配对；配不上对的孤儿记录比没有记录更难查。
- **第 ⑤ 关在处理器之前。** 一批注定被拒的图片不该先落盘再删。

### 同一个名字，不同的 agent 可以是不同的实现

```mermaid
flowchart TD
    G["全局登记<br/>/status → 通用实现"] --> A1
    G --> A2
    S["子 agent 自己的登记<br/>/status → 它自己的实现"] --> A2
    A1["主 agent<br/>敲 /status 走通用实现"]
    A2["子 agent<br/>敲 /status 走自己那个"]
```

近的盖住远的。这样一个子 agent 可以换掉某条命令的行为，而不必去改全局那份。

### 停不下不合作的处理器

取消赢了那一局，这次执行就结算成「取消」并落账，但**那个处理器的协程还在跑**：

```mermaid
sequenceDiagram
    participant U as 人
    participant R as 注册表
    participant H as 处理器
    U->>R: 取消
    R->>R: 立刻结算成 cancelled，落账
    R-->>U: 返回
    Note over H: 还在跑，没人能掐死它
    H-->>R: 迟到的结果，丢弃
```

Go 没有掐死别人协程的办法，所以这里如实说明，而不是假装停住了。

## 向人发问：这个包自己不问任何人

### 它是一个插槽

```mermaid
flowchart LR
    ASK["Ask（一批问题）"] --> GATE{"这道门"}
    GATE -->|"形状就不对"| REJ["当场拒<br/>请求根本没离开进程"]
    GATE -->|"过了"| P["提供方<br/>一个上下文里只准有一个活着的"]
    P --> UI(("终端 / 桌面 / 网页"))
    UI --> ANS["人的回答"]
```

**为什么门要设在这里，不设在每个界面里**：错的是提问方。一个界面就算发现了这批问题有毛病，它也只能把一个坏问题画得好看一点。

### 没有提供方是什么后果

```mermaid
flowchart LR
    A["模型想问一句"] --> B{"接了提供方吗"}
    B -->|"接了"| C["停下来等人"]
    B -->|"没接"| D["明确失败<br/>不是无限等待"]
```

一个批处理装配根本不装这个插头，模型也就问不出问题来——这不是缺陷，是这条设计想要的结果。

## ask_user：模型那一侧的入口

这个包薄到只做**形状转换**，一个判断都不做：

```mermaid
sequenceDiagram
    participant M as 模型
    participant T as ask_user 工具
    participant S as 发问接缝
    participant U as 人
    M->>T: 一批 snake_case 的问题参数
    T->>S: 翻成接缝要的形状
    S->>S: 空问题？意图对不上？在这里拒
    S->>U: 摆到人面前
    U-->>S: 回答
    S-->>T: 结构化答案
    T-->>M: 翻回模型看得懂的形状
```

**拒绝的话术只有一份**：接缝报什么错，就原样成为这次工具调用的失败，工具层会把错误的身份原样带给模型，模型不必去解析错误文本。

## 审批：一次「要不要放这个工具过去」

### 三道关，顺序是设计的一部分

```mermaid
flowchart TD
    A["某个工具要动手"] --> B{"① 现在有打开的回合吗"}
    B -->|"没有"| X["当场拒<br/>一个字节都不写"]
    B -->|"有"| C{"② 这个会话的策略是「从不打扰」吗"}
    C -->|"是"| R["直接判成驳回<br/>连派发都不派发"]
    C -->|"不是"| D["③ 交给接上来的答复者"]
    D --> E{"有人应答吗"}
    E -->|"应答了合法的值"| F["放行一次 / 驳回"]
    E -->|"没人应答"| U["不可用"]
    E -->|"应答的自己报错"| U
    E -->|"应答了一个词汇表外的值"| U
```

三个「为什么」：

- **① 为什么必须在回合里。** 问和答这一对是审计记录，必须被回合圈住。两个回合之间裸写的一条事件，重新装载时和一段崩溃残尾长得一模一样，会被静静丢掉。
- **② 为什么策略闸不做成一条答复者。** 做成答复者的话，任何一条后登记的答复者都可能排在它前面，「从不打扰就必然驳回」这句承诺就变成取决于登记顺序了。
- **③ 为什么三种意外都收敛成「不可用」。** 失败一律往**不放行**那一侧倒。

### 取消赢了，迟到的答复怎么办

```mermaid
sequenceDiagram
    participant C as 调用方
    participant S as 审批服务
    participant A as 答复者
    C->>S: 请求
    S->>A: 派发（跑在自己的协程里）
    C->>S: 取消
    S-->>C: 立刻结算成 cancelled
    A-->>S: 迟到的答复送进一个只装一个的信箱
    Note over S: 送得出去、收得掉，然后被丢弃
```

信箱容量是 1，为的是让那个答复者**送得出去**——否则它会永远卡在发送上，泄漏一条协程。

### 一次放行只管这一次

```mermaid
flowchart LR
    A["这次放行"] --> B["这一次工具执行"]
    A -.->|"不是"| C["身份认证"]
    A -.->|"不是"| D["长期权限授予"]
    A -.->|"不是"| E["下一次同样的操作"]
```

## 权限预设：给用户看的档位

### 为什么要有档位

底层旋钮是给部署方拨的，不是给用户拨的。档位把旋钮包成一份**起好名字、写好说明**的单子：

```mermaid
flowchart TD
    subgraph TB["部署方配的一张单子（必填，没有默认）"]
        G["guarded<br/>每次动手前先问 → 审批策略 = 问"]
        T["trusted<br/>放手做，不再打断 → 审批策略 = 从不打扰"]
    end
    U(("用户")) -->|"按名字挑一档"| TB
    TB --> W1["① 记下「他挑的是哪个名字」"]
    TB --> W2["② 把审批策略拨过去<br/>走它自己那条正规写路径"]
    W1 --> LOG[("会话日志<br/>唯一的账")]
    W2 --> LOG
    LOG --> UI["界面回读"]
```

### 为什么①要单独记一笔

因为**两个档位完全可以拨出同一份旋钮值**：

```mermaid
flowchart LR
    subgraph BAD["只看旋钮"]
        A1["用户挑了 careful"] --> V1["策略 = 问"]
        A2["另一档 balanced"] --> V1
        V1 --> D1["界面显示：balanced<br/>（挑的那一下丢了）"]
    end
```

```mermaid
flowchart LR
    subgraph GOOD["另记一笔名字"]
        B1["用户挑了 careful"] --> N["日志里记着：careful"]
        B1 --> V2["策略 = 问"]
        N --> D2["旋钮还对得上时优先认这个名字<br/>界面显示：careful"]
    end
```

那条记名字的事实**只进日志、不进模型誊本**——它是给界面看的，模型不需要知道用户点的是哪个按钮。

### custom 不是一个能挑的档位

用户绕过档位直接改了底层旋钮，旋钮值配不上任何一条单子，这时当前值显示成 `custom`：

```mermaid
flowchart LR
    K["当前旋钮值"] --> M{"配得上单子上某一条吗"}
    M -->|"配得上"| N["显示那一条的名字"]
    M -->|"配不上"| C["显示 custom"]
    C -.->|"永远不会被写进那条「挑了谁」的记录"| X["×"]
    C -.->|"不能作为切换目标"| X
```

### 这个 Go 版本只捆一个旋钮

DSH 的档位捆两样：沙箱模式 + 审批策略。沙箱那一整支在本仓库判为不需要（理由见[文件系统](filesystem.md)），所以：

```mermaid
flowchart LR
    subgraph DSH["DSH 的档位"]
        S1["沙箱模式"]
        S2["审批策略"]
    end
    subgraph GO["这里的档位"]
        S3["审批策略"]
    end
    DSH -->|"沙箱整支判为不需要"| GO
```

连带的两个后果：**不带默认档位表**（DSH 那两条默认档位是照沙箱模式起名的，照录过来会给用户看到一个叫「完全访问」、却根本不管文件访问的选项），以及**档位表必填**。

计划模式也没有折进来当第二个旋钮——沙箱和审批各自独立地施加限制，它们不读也不写计划状态，DSH 是刻意把计划模式挡在这个捆包外面的，这里跟着挡。

## 生命周期与并发

```mermaid
flowchart LR
    R1["注册一条命令"] --> U1["拿回一个撤销函数"]
    R2["接一个发问提供方"] --> U2["拿回一个撤销函数"]
    R3["接一个审批答复者"] --> U3["拿回一个撤销函数"]
    U1 --> D["撤销后：新的调用进不来"]
    U2 --> D
    U3 --> D
```

- 一个请求的答复**只收一次**，取消沿调用链传播。
- 策略变更写进目标会话，恢复之后可以重新折出当前有效策略——不靠内存里那份。
- 用户回调**不在注册表的锁里执行**，所以一个回调可以安全地反过来再查这些服务。

## 失败语义

```mermaid
flowchart TD
    A["出了岔子"] --> B{"哪一类"}
    B -->|"没有提供方 / 没有答复者"| C["明确失败<br/>绝不无限等待"]
    B -->|"人主动取消"| D["cancelled"]
    B -->|"调用链的 context 取消"| E["和上面那条是不同的错<br/>不合并"]
    B -->|"人给了个非法回答"| F["非法回答<br/>也和取消分开"]
    B -->|"审批这一侧的任何意外"| G["收敛成「不可用」<br/>往不放行那侧倒"]
    B -->|"命令的生命周期事件写不进去"| H["不发布成功结果<br/>已经发生的外部副作用也不伪造回滚"]
```

最后一条值得单说：一条命令已经把文件改了，事后日志写失败，这里**不会**假装那次修改没发生——伪造一次回滚比留下一条失败记录危险得多。

## 能力边界

```mermaid
flowchart TD
    Y["这五个包做的"] --> Y1["登记、准入、派发、落账"]
    Y --> Y2["把问题和请示送到插头上"]
    Y --> Y3["把档位翻成旋钮值"]
    N["这五个包不做的"] --> N1["不画任何界面<br/>网页、终端、移动端都不在这里"]
    N --> N2["不是 shell 解释器<br/>参数原样交给处理器"]
    N --> N3["不定义任何一条命令<br/>表是插件自己填的"]
    N --> N4["审批不是身份认证<br/>也不是长期授权"]
    N --> N5["档位一个权限判定都不做<br/>真正拦人的是审批那一层"]
    N --> N6["在宿主声明不可暂停的位置<br/>不能强行把 agent 停住去问人"]
```
