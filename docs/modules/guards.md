# 运行时 Guard

对应包：`feature/guard/repeattoolreminder`、`feature/guard/repeattoolcap`、`feature/guard/timeoutpolicy`

## 定位

模型自己动手干活的时候，有两个毛病是必然会出现的，而且都不是模型「变笨了」，是这类系统的固有形状：

```mermaid
flowchart LR
    P1["毛病一：原地打转<br/>同一个工具连着调个没完"] --> R1["重复调用提醒<br/>（劝一句）"]
    P1 --> R3["连续调用上限<br/>（拦下来）"]
    P2["毛病二：一次调用回不来<br/>模型和用户一起干等"] --> R2["超时策略"]
```

毛病一有两层，因为劝告和拦截是两件不同的事，谁也替不了谁——见下面「劝告和闸门为什么都要有」。

### 原地打转长什么样

```mermaid
flowchart TD
    A["模型：读这个文件"] --> B["拿到一份结果<br/>但它没读懂 / 没找到想要的"]
    B --> C["模型：读这个文件<br/>（一模一样的参数）"]
    C --> B
    C -.->|"没人打断的话<br/>这一圈能转到把预算烧光"| B
```

用户那边看到的是：进度条一直在动，模型一直在「工作」，可什么都没往前走。账单照收。

### 一次调用回不来长什么样

```mermaid
flowchart TD
    A["模型：跑这条命令"] --> B["命令连上了一台不响应的机器"]
    B --> C["这一步永远不结束"]
    C --> D["整个会话卡在这儿"]
    D -.->|"模型没有别的路可走<br/>因为它在等这次调用的结果"| C
```

### 劝告和闸门为什么都要有

先说为什么劝告不够：

```mermaid
flowchart TD
    A["提醒那一层说：<br/>「你在重复同一次调用」"] --> B{"模型听不听"}
    B -->|"听"| C["它换条路，问题就没了"]
    B -->|"不听"| D["它接着调"]
    D --> E["agent 循环没有步数上限<br/>只有模型不再发工具调用时才收场"]
    E --> F["一个不听劝的模型可以一直调下去<br/>唯一的边界是把上下文撑爆"]
    F -.->|"那是事故，不是刹车"| F
```

再说为什么闸门不能替掉劝告：

```mermaid
flowchart LR
    subgraph W["如果只留闸门"]
        A1["第三次重复：直接拒绝"] --> A2["可是分页遍历第三页<br/>也长得一模一样"]
        A2 --> A3["把正常的活儿掐了"]
    end
```

**「连着调同一个工具」并不总是错的**。一次分页遍历、一次轮询、按顺序写十个文件，在调用记录上和死循环长得完全一样，只有模型自己知道它在干什么。所以两层的分工是这样的：

```mermaid
flowchart TD
    R["重复调用提醒"] --> R1["认「同名 ＋ 同参」——精确"]
    R --> R2["只捎一句话，从不拦——所以可以对所有工具开着"]
    R --> R3["治的是「模型自己没发现在打转」"]
    C["连续调用上限"] --> C1["只认工具名——粗"]
    C --> C2["到顶就拒绝派发"]
    C --> C3["默认一个工具都不限<br/>每个上限都得手写出来"]
    C --> C4["治的是「劝了也不听」"]
```

前者精确但拦不住，后者粗但一定生效。两层并存不冲突，装的次序也不影响谁。

超时那一层的克制比这两层都彻底——它连「停下来」都做不到，只能改写模型看到的结果。这一点必须说在最前面，否则「设了超时」很容易被读成「超时了就不跑了」。

## 架构

三层挂在工具管线的三个不同位置上：

```mermaid
flowchart TD
    M(("模型")) -->|"我要调这个工具"| PRE["执行前这条链<br/>参数校验、审批<br/>【连续调用上限在这里】"]
    PRE -->|"到顶了：直接回一份拒绝<br/>后面一步都不走"| RES
    PRE --> AROUND["绕派发这一圈<br/>【超时策略在这里】"]
    AROUND --> EXEC["工具的执行体"]
    EXEC --> AROUND
    AROUND --> POST["执行后这条链<br/>【重复调用提醒在这里】"]
    POST --> RES["交回模型的那份结果<br/>＋ 捎带的上下文消息"]
    RES --> M
```

```mermaid
flowchart LR
    C["连续调用上限：挡在执行体前面"] --> C1["因为它要在派发之前<br/>就能把这次调用拒掉"]
    A["超时策略：包在执行体外面"] --> A1["因为它要给执行体<br/>递一条有期限的取消线"]
    B["重复调用提醒：跟在执行体后面"] --> B1["因为它要往结果上<br/>再挂一条消息"]
```

一次调用穿过三层的完整走法：

```mermaid
sequenceDiagram
    participant M as 模型
    participant G as 连续调用上限
    participant T as 超时策略
    participant X as 工具执行体
    participant R as 重复调用提醒
    M->>G: 调用请求
    G->>G: 这个工具连着调第几次了
    G->>T: 没到顶，放过去
    T->>T: 查这个工具声明了多长的预算
    T->>X: 带着期限进去
    X-->>T: 结果（或者被期限打断）
    T->>T: 期限赢了就把结果整个换掉
    T->>R: 把结果往后传
    R->>R: 这次调用和上一次一样吗
    R-->>M: 结果 ＋ 可能捎上的那句提醒
```

到顶那一次走的是另一条路：

```mermaid
sequenceDiagram
    participant M as 模型
    participant G as 连续调用上限
    participant X as 工具执行体
    M->>G: 调用请求
    G->>G: 已经超过上限了
    G-->>M: 一份失败结果，正文是一句说明
    Note over X: 执行体一行都没跑
```

### 三层互不知道对方

```mermaid
flowchart TD
    A["谁也不认识谁"] --> C["装一个不装另一个<br/>装的次序换过来"]
    C --> D["行为都不变"]
    D -.->|"这是故意的：<br/>三条规则各管各的一件事"| C
    E["唯一的例外：到顶那一次是短路的"] --> F["它不往后走，所以执行前那条链上<br/>排在它后面的规则不会跑"]
    F -.->|"必须这样：让后面某条规则<br/>把它改回放行，这道刹车就等于没有"| F
```

## 重复调用提醒

### 什么算「同一次调用」

```mermaid
flowchart TD
    A["工具名"] --> K["合成一个身份"]
    B["参数"] --> N["先解开再按键名排好序<br/>让两份只是写法顺序不同的参数<br/>算成同一份"]
    N --> K
    K --> C{"和上一次的身份一样吗"}
    C -->|"一样"| D["次数加一"]
    C -->|"不一样"| E["次数归一，重新起一条链"]
```

参数解不开的时候（模型吐了一段坏 JSON）就原样当字符串比。这只降低**判定的精度**——两份写法不同的坏 JSON 会被当成两次不同的调用——不会把不同的调用错认成同一次。

### 三件事能把链断掉

```mermaid
flowchart LR
    C["一条正在增长的链"] --> B1["换了工具"]
    C --> B2["换了参数"]
    C --> B3["用户插了话"]
    B1 --> Z["链断掉，从头数"]
    B2 --> Z
    B3 --> Z
    B3 -.->|"用户重新说了一句话<br/>之后的场景已经不同了<br/>跨过它的重复不算循环"| Z
```

前两件这一层自己认得出；第三件要靠 agent 循环在每一步之前叫一下它。**判断留在本包，接线留给循环**——这样这条规则在循环写好之前就能被完整地测到。

### 越劝越具体

```mermaid
flowchart TD
    A["第 3 次"] --> A1["客气话：<br/>「你在重复同一次调用，<br/>先仔细看看上一次的结果」"]
    B["第 5 次"] --> B1["点名道姓：<br/>工具名 ＋ 连续次数 ＋ 那份参数"]
    C["第 8 次"] --> C1["同上，次数更难看"]
    D["第 4、6、7 次"] --> D1["一句话都不说"]
    D1 -.->|"每次都说等于变成噪声<br/>模型会学会忽略它"| D1
```

三级阈值可以配，但配上去的那几级里**最小的那一级**说客气话，其余的说详细话。绑的是次序而不是写死的数字，所以改了阈值之后「先客气、后详细」这个关系仍然成立。

### 参数只在文案里截断，判定永远看完整的

```mermaid
flowchart LR
    A["一次写文件的调用<br/>参数里带着整篇正文"] --> B{"两个去处"}
    B --> C["链的身份：用完整的那一份"]
    B --> D["给模型看的那句话：截到五百字"]
    D -.->|"不截的话，那篇正文会原样<br/>搭车进下一次请求——<br/>而这正好发生在一个<br/>已经在打转的场景里"| D
```

### 为什么计数落在执行**后**

```mermaid
flowchart TD
    A["一次被守卫拒绝的调用"] --> B{"计在执行前还是执行后"}
    B -->|"执行前"| C["被拒的那些也数<br/>但拒绝要到后面才发生"]
    B -->|"执行后（当前做法）"| D["被拒的那些照样数得着"]
    D --> E["一个反复撞同一道拒绝的模型<br/>正是最该被打断的那种循环"]
```

而且计数在往后传之**前**就完成：链的状态只记「模型又调了一次」，和后面那些层最终怎么裁决无关。

### 没被跟踪的工具是透明的

```mermaid
flowchart LR
    subgraph BAD["如果把没跟踪的调用当成断点"]
        A1["同样的命令"] --> A2["中间夹一次无关的小工具"] --> A3["同样的命令"]
        A3 --> A4["链断了，一次提醒都不会有"]
        A4 -.->|"等于给模型留了一个<br/>随手就能甩掉这层的口子"| A4
    end
```

```mermaid
flowchart LR
    subgraph GOOD["实际做法：既不计数也不断链"]
        B1["同样的命令"] --> B2["中间夹一次无关的小工具<br/>（这一层当没看见）"] --> B3["同样的命令"]
        B3 --> B4["仍然是连着的两次"]
    end
```

### 那句提醒插在最前面，而且署名

```mermaid
flowchart TD
    A["这次调用捎带的那批上下文消息"] --> B["提醒放在第一条"]
    B --> C["后面那些层自己挂的<br/>原样留在后面"]
    D["每条提醒都盖一个来源标签"] --> E{"如果不盖"}
    E --> F["模型下一轮会把它<br/>当成用户在催自己"]
    F -.->|"所以这个标签是承重的"| D
```

被拦下的调用一样收得到这句提醒——拦不拦是别的层的事，摆事实是这一层的事。

## 连续调用上限

### 只认工具名，不认参数

```mermaid
flowchart TD
    A["要挡的是哪种打转"] --> B["「每次换一点参数<br/>看起来像有进展」的那种"]
    B --> C{"如果这一层也认参数"}
    C --> D["模型在参数里加一个空格<br/>就把这一层甩掉了"]
    D -.->|"而那恰好是打转时<br/>最常发生的事"| D
    C --> E["所以只认工具名"]
```

这和提醒那一层是反过来的取舍，两边都对，因为要治的毛病不同：提醒要精确（错报一次就是噪声），闸门要甩不掉（漏一次就等于没有）。

### 代价：会误伤，所以默认什么都不限

```mermaid
flowchart TD
    A["同一个工具连着调很多次<br/>的合法场景"] --> A1["分页遍历"]
    A --> A2["轮询等一件事完成"]
    A --> A3["按顺序写十个文件"]
    A1 --> B["只认名字的话<br/>这些一个都躲不过去"]
    A2 --> B
    A3 --> B
    B --> C["所以这一层默认一个工具都不限"]
    C --> D["每个上限都必须显式写出来"]
    D -.->|"给一个会误伤的默认值<br/>等于让每个接入方先踩一次坑"| D
```

上限写在配置里，按工具名精确匹配，**不支持通配**。提醒那一层的圈选是支持通配的——差别有理由：多劝一个工具没有代价，圈错一个只是多一句话；这一层会拒绝调用，圈错一个就是一次线上故障，所以要求把名字一个一个写出来。

### 什么会把计数清零

```mermaid
flowchart LR
    C["一条正在增长的计数"] --> B1["换了另一个<br/>同样配了上限的工具"]
    C --> B2["用户插了话"]
    B1 --> Z["计数清零，从头数"]
    B2 --> Z
    B2 -.->|"用户重新说了一句话<br/>之后的场景已经不同了<br/>跨过它的重复不是打转"| Z
```

和提醒那一层一样，**没配上限的工具是透明的**：它既不计数，也不清零。把它当成断点，等于给模型留一个「两次之间插一次小工具就能甩掉这道闸」的口子。代价是这里数的「连续」比字面意思宽——中间隔着多少次没配上限的调用都不算断。要让某个工具能断链，就给它也配一个上限。

**没有「结果不一样就清零」这一条。**一次成功和一次失败在这一层眼里没有区别——判断这次结果算不算进展是模型的事，这一层只数次数。

### 到顶之后还在撞怎么办

```mermaid
flowchart TD
    A["先计数，再判断"] --> B["撞了上限之后<br/>计数会继续涨"]
    B --> C["第 4 次、第 5 次<br/>照样被拦"]
    C -.->|"一个反复撞同一道拒绝的模型<br/>不该因为撞得多了反而被放行"| C
```

### 拒绝那句话必须说三件事

```mermaid
flowchart TD
    A["给模型的那句话"] --> B["1. 拦了"]
    A --> C["2. 为什么拦<br/>（连着调了几次、上限是几）"]
    A --> D["3. 接下来该干什么<br/>（用已有的结果回答、换个工具、<br/>或者说清楚还缺什么）"]
    E{"只说「不许调」会怎样"} --> F["模型最常见的反应是<br/>换个参数再来一次"]
    F --> G["它换得再多也还是被拦<br/>于是两边一起空转"]
```

### DSH 没有这一层

上游 DSH 只有提醒那一层。这一层是本仓库自己加的，理由就是上面「劝告和闸门为什么都要有」那一段：劝告拦不住一个不听劝的模型，而 agent 循环本身没有步数上限。

## 超时策略

### 「协作式」是这个包唯一的前提

```mermaid
flowchart LR
    subgraph WRONG["容易产生的误解"]
        A1["设了超时"] --> A2["超时了那段代码就停了"]
        A2 --> A3["资源也就放回来了"]
    end
```

```mermaid
flowchart LR
    subgraph RIGHT["实际发生的事"]
        B1["设了超时"] --> B2["期限到了，给执行体递一个「该收手了」的信号"]
        B2 --> B3{"执行体理会这个信号吗"}
        B3 -->|"理会"| B4["它自己收手"]
        B3 -->|"不理会"| B5["它接着跑到底<br/>占着的连接和内存还占着"]
        B4 --> B6["模型那边一律看到一份超时结果"]
        B5 --> B6
    end
```

**变的只是模型收到的那份结果**，不是那段代码的命运。一个工具写下自己的时间预算，就是在向这一层保证：它会把这个「该收手了」的信号一路转发给真正干活的那一段。

### 预算从哪儿来，为什么每次都要重查

```mermaid
flowchart TD
    A["一次调用进来"] --> B["按这次调用的 agent<br/>去解析这个工具名"]
    B --> C{"解出来的定义上<br/>写了时间预算吗"}
    C -->|"没写"| D["原样放过，这一层不管"]
    C -->|"写了"| E["按这个预算挂一条期限"]
    F["为什么不在安装的时候查一次存起来"] -.->|"同一个工具名在不同 agent 眼里<br/>可能解析到不同的定义"| B
```

```mermaid
flowchart TD
    A["解不出这个工具"] --> B["也原样放过"]
    B --> C["这次派发接下来会以<br/>「找不到这个工具」失败"]
    C -.->|"那句诊断比这一层<br/>现编一个超时有用得多"| C
```

### 分辨「是我超时了」还是「别人取消了」

这是整层最要紧的一处判断：

```mermaid
flowchart TD
    A["这次调用被取消了"] --> B{"取消的原因上<br/>盖的是本层那个代号吗"}
    B -->|"是"| C["我的期限赢了<br/>把结果整个换成一份超时"]
    B -->|"不是"| D["是别人取消的<br/>结果和错误一律原样往上传"]
    D --> E["可能是用户按了停止<br/>也可能是外面一层更早的期限"]
```

```mermaid
flowchart LR
    A["为什么必须分开"] --> B["超时：可以换个更小的输入再试一次"]
    A --> C["用户按停止：绝不能重试"]
    B -.->|"只有一个「已取消」的布尔值<br/>这两件事就分不开了"| C
```

### 期限赢了之后为什么要把结果整个换掉

```mermaid
flowchart TD
    A["执行体看见取消之后<br/>交出来的东西"] --> B["可能是它自己的一份「已取消」"]
    A --> C["也可能是一份跑了一半的成功值"]
    B --> D["模型从这两种里都读不出「是超时」"]
    C --> D
    D --> E["所以换成一份带固定代号的超时结果"]
    E --> F["模型读得懂：该缩小范围重试"]
    E --> G["别的层读得懂：能按这个代号<br/>路由重试策略、沙箱策略和回放"]
```

那份换上去的结果里，一句人话的错误消息、一个给机器路由用的代号、一个给人看的错误名，三样都在。这个形状是这一层对别的层的承诺，不跟着任何内部改法走。

### 完整时序

```mermaid
sequenceDiagram
    participant C as 调用方
    participant P as 超时策略
    participant X as 工具执行体
    C->>P: 派发一次调用
    P->>P: 在调用方那条取消线之下<br/>挂一条自己的期限
    P->>X: 递进去
    Note over X: 期限到了
    X-->>P: 它自己那份收敛结果（作废）
    P->>P: 确认这条期限是自己挂的
    P-->>C: 一份带超时代号的结果
```

那条期限**必须从调用方那条线上派生**。这是这一圈里唯一不许犯的错——递一条不相干的取消线进去，等于把调用方停止这次调用的能力摘掉了。

## 生命周期与并发

```mermaid
flowchart TD
    A["三层都用同一种方式安装"] --> B["交回一个撤销函数"]
    B --> C["跟着它所属的作用域一起收回"]
    D["安装时给的作用域<br/>决定它管哪些 agent"] --> E["没有身份的作用域：管所有 agent"]
    D --> F["有身份的作用域：只管那条链下面的"]
```

数重复的那两层各有两个安装函数，因为它们要挂在两张不同的注册表上：

```mermaid
flowchart LR
    A["装在工具注册表上的那条"] --> A1["管计数<br/>（提醒那层顺带发提醒<br/>上限那层顺带拦）"]
    B["装在 agent 注册表上的那条"] --> B1["管「用户插话就清零」"]
    C["只装前一个也跑得动"] --> C1["代价是用户插话不再清零"]
    C1 -.->|"对上限那层来说，那意味着<br/>用户明确要求「再查一次」时<br/>模型会撞在一道本该松开的闸上"| C1
```

判断和接线分开还有一个好处：这两条规则不依赖 agent 循环就能被完整地测到。

```mermaid
flowchart LR
    A["计数按 agent 分开存"] --> B["一把互斥锁护着"]
    B --> C["因为工具调用可能是并行发出、并行回来的"]
    D["超时那一层没有共享状态"] --> E["一次调用的期限只活在那一次调用里<br/>函数返回就没人拿得到了"]
```

一处 Go 特有的安排：

```mermaid
flowchart TD
    A["DSH 把每个 agent 那份计数<br/>挂在以 agent 对象为键的弱引用结构上"] --> B["靠垃圾回收顺手清掉"]
    C["Go 这边用的是弱指针做键"] --> D["键死掉的那些条目<br/>在下一次写入时顺手扫掉"]
    D --> E["扫的代价是走一遍<br/>活着的 agent（几十个）"]
    E -.->|"比维护一个「攒够多少条才扫」的旋钮便宜<br/>也少一个调不准就退化成泄漏的开关"| E
```

DSH 那边还有一步「把执行体身上的取消信号换回原来那条」，Go 这边没有对应物：取消在 Go 里是**参数**不是字段，派生出来的那条线只递给执行体，函数一返回就没人拿得到它了。没有要还原的东西，也就没有还原时机出错的可能。

## 失败语义

```mermaid
flowchart TD
    A["出了岔子"] --> B{"哪一类"}
    B -->|"提醒那层的配置不成立<br/>（阈值给了空的、写了两遍、小于二）"| C["造这一层的时候当场失败<br/>绝不静默退回缺省值"]
    B -->|"上限那层的配置不成立<br/>（工具名是空的、上限小于一）"| C
    B -->|"工具自己业务上失败了"| D["三层都不改写<br/>原样交回模型"]
    B -->|"期限到了"| E["只说明期限到了<br/>不证明那段代码已经停下<br/>更不证明它回滚过"]
    B -->|"取消来自别处"| F["原样往上传<br/>不冒充成自己的超时"]
    B -->|"次数还没到"| G["什么都不做<br/>这不是失败"]
```

配置错了要**响亮地**失败。对上限那一层尤其要紧：一份写着上限的配置表达的是「我要拦」，把它读成「那就不拦」，等于让一次配置错误变成一道永远不会响的刹车。

## 能力边界

```mermaid
flowchart TD
    Y["这三层做的"] --> Y1["认出机械重复，并把这件事<br/>说给模型听"]
    Y --> Y2["给配了上限的工具设一道硬闸<br/>到顶就不派发"]
    Y --> Y3["给声明了预算的工具挂上期限<br/>并把超时翻译成模型读得懂的结果"]
    N["不做的"] --> N1["提醒那层不拦调用，也不改写正常结果"]
    N --> N2["不判断一次重复到底是不是错的"]
    N --> N3["上限那层不给默认值<br/>没配到的工具一次都不限"]
    N --> N4["不管一个回合总共调了多少次工具<br/>数的是连续，要管总量得另设一层"]
    N --> N5["不替工具声明预算<br/>没写预算的工具超时那层不管"]
    N --> N6["不做进程隔离，也不回收资源<br/>谁开的连接和句柄谁收"]
    N --> N7["不重试<br/>要不要再来一次是读到结果的模型的事"]
    N --> N8["不是策略语言，不做内容审核<br/>也不做业务风控"]
```

授权和用户审批不在这三层：那是工具管线上另外一段的事。
